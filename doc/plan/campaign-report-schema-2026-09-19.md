# 投放分析输出方案：轻量卡通分析仪表盘

状态：设计提案，未接入业务代码、未部署。基线为 PR #61 / `6c93bd9`。

后续架构方案：[场景、Plan、Skill、Tool 与 Graph](campaign-agent-architecture-2026-09-19.md)。执行与图文报告以该方案及其合同附件为准；本文保留视觉探索过程，下面的固定卡片数、短解释与 Narrative Schema 不作为生产合同。

最新设计修正：用户要求保留分析深度，用仪表盘与文本穿插呼应；不能把每个分析强制缩成一句话。本轮先交付效果图。下述 Narrative Schema 的条数和短文本限制属于早期草案，已被这一要求取代，暂不作为实现合同；后续应改为可重复的分析章节、分段解读和证据引用。

## 1. 设计方向

采用「轻量卡通仪表盘 + 分段分析」。围绕本次问题组织数据，不固定堆满全部统计维度；每块图表自带发现、解释、口径和证据入口。用户先看到结论和关键数字，再沿着图表、分析和验证路径阅读完整报告。

保留现有木星主题、导航及提问入口。参考 design-taste-frontend 的改版审查／保留品牌原则；本页面属于产品分析工作台，采用当前 Vue 组件与品牌令牌，不套用营销首页的大标题、装饰动画或 React 默认栈。建议设计参数：差异度 5、动效 2、信息密度 6。

现有令牌：背景 `#f5f9ff`，白色卡片，正文 `#182847`，主色 `#2f55e7`，点缀 `#ffd665`，边框 `#d7e1ee`，圆角 16px，中文沿用 Noto Sans SC／MiSans／微软雅黑。卡通感集中在小型木星角色、结论标签、轻描边与少量错位阴影；图表和数据表保持规整，不在每张卡片重复放机器人。

### 已确认的问题

- `AgentRunResult` 只有自由文本 `answer` 和无类型列表，没有统一报告与结果状态协议。
- `AgentReport.vue` 主区为长正文，右侧优先显示证据目录与执行概况，数据与解释分离。
- `AgentResultDetails.vue` 已能展示对比／排名／下钻表格，但需要离开主报告查看；普通统计多为 JSON。
- `agentWorkspace.js` 将当前和历史结果默认称为「完整结果」，导出仍大量附加 JSON，无法准确表达失败、部分数据及任务等待。
- 本轮仅作源码审查；未启动 Docker、浏览器验收或业务实现。

## 2. 报告模块与展示规则

| 模块 | 展示形式 | 内容来源 | 规则 |
| --- | --- | --- | --- |
| 分析范围与状态 | 一行对象、日期、时区、数据状态 | 后端已解析范围及工具状态 | 不使用仅提交的分组标签冒充实际范围；多对象可展开 |
| 一句话结论 | 窄结论条 + 小型木星角色 | 后端事实标题，模型补充短解释 | 标题约 24 字；不超过两行，禁止无依据的效果归因 |
| 关键指标带 | 通常 PV／UV／UIP，必要时加一个与问题相关的派生指标 | 后端指标绑定 | 3–4 个槽位；无效项不凑数；未知为「—」，真实零值为 0；增长率仅在可比较时显示 |
| 主分析卡 | 一个主要图表 + 一句发现 + 口径问号 | 后端数据集，模型引用已计算事实 | 趋势、对比、排名、下钻按问题切换；单次一个视觉主角 |
| 辅助分析卡 | 小型排名／结构条形图 + 一句解读 | 本次已有且相关的数据 | 0–2 块；没有对应证据就不显示，不为填满布局补查无关维度 |
| 下一步分析 | 1–3 个短建议或追问按钮 | 模型选择后端可用动作候选 | 明确「建议核查」；用户点击后确认／提交新查询，不自动执行预算或投放变更 |
| 数据说明与依据 | 关键限制常显 + 口径悬停 + 证据抽屉 | 后端质量与审计引用 | 影响结论的缺口不得只藏在 tooltip；执行轨迹置于诊断入口 |

避免单块连续长文。章节通用结构为：**问题／发现 → 数据图 → 分段解读 → 原因假设与反证 → 下一步验证 → 证据入口**。复杂分析可以扩展多个章节，必要论证直接在正文中分段呈现，不因字数移入折叠区。观察与原因假设明确区分，假设须标「待验证」。一段围绕一个论点，段落之间用对应图表、事实标记或对比表衔接；按分析需要决定深度，不按卡片数量裁剪内容。

## 3. 前端布局

设计示意图：[主报告示意](../design/campaign-report-2026-09-19.png)。图片是虚构数据的布局概念，不是运行截图。

```text
现有页面标题／导航
┌ 分组 · 实际期间 · 时区 · 数据状态             复制／导出／继续分析 ┐
│ 小木星  一句话结论                                                │
├───────────────────────────────────────────────────────────────┤
│  PV 主指标           UV                UIP          相关变化     │
├────────────────────────────────────┬──────────────────────────┤
│ 主分析图：趋势／对比／排名            │ 辅助证据：短链贡献或结构    │
│                                    │ 图表                      │
│ 图上的事实标记                      │ 一句发现 + 依据           │
│ 一句发现 + 短解释 + 依据              ├──────────────────────────┤
│                                    │ 下一步：短建议／追问       │
├────────────────────────────────────┴──────────────────────────┤
│ 数据限制：关键限制常显                      数据说明／执行记录    │
└───────────────────────────────────────────────────────────────┘
```

- 桌面按**报告可用宽度**而非屏幕宽度断点：≥1100px 用 12 列，主卡 8 列、辅助区 4 列；列距 16px，卡片内边距 20–24px。主卡目标高度 380–420px，绘图区 220–260px；右侧辅助卡 220–260px、下一步 140–160px。高度允许内容撑开，不裁剪文本。
- 指标采用一条约 96–112px 高的带状分区；主指标稍突出，其余用分隔线，避免四张等权大卡占满首屏。没有有效比较时自动收为三个指标。
- 可用宽度 800–1099px：主卡独占一行，下方两块辅助并排。更窄时单列；手机指标 2 列，按钮保留文字，表格可展开或分页。阅读区正文至少 14px。
- 报告区域单一纵向阅读滚动；卡片正文不设独立滚动条。复杂数据表以分页／明细抽屉承载，保留表格必要的横向滚动。
- 省份图仅在地域问题中成为主卡；不用彩色地图当常驻装饰。无地图数据、分类不匹配或样本过少时改为条形图／状态说明。
- 图表动画仅用于轻量过渡，尊重减少动态效果设置；悬停可用键盘焦点等效访问，点击「依据」打开有焦点管理的详情。

## 4. 不同问题的可视化模板

| 问题 | 主图 | 辅助内容 | 避免的表达 |
| --- | --- | --- | --- |
| 趋势与高峰 | 日趋势折线；高峰问题可加小时柱形图 | 最高点／变化点的后端事实标记 | 缺失时间点补零；同时画六条尺度不同的线 |
| 多期间／多对象对比 | 分组柱形图或两期哑铃图 | 基期、当前、绝对差和可用变化率的紧凑表 | 不等长／未完成／部分期间仍给确定增长；把重叠 UV 相加 |
| 短链排名 | 横向条形图，默认 Top 5 | 完整结果表与范围说明 | 将 Top N 当全量；只按已读取一页排名 |
| 单维结构 | 横向占比条形图 | UNKNOWN／不适用单独列示 | 用 UV／UIP 画可加总份额；把未知当直接访问 |
| 地域分析 | 省份热点图 + Top 5 条形图 | 未知地域、地域定义、采集覆盖 | 以 IP 地域推断用户真实所在地 |
| 双维下钻 | 稀疏数据用分组条形图；密集数据才用热力矩阵 | 单元格 PV 与样本数 | 5000 桶同时绘制；仅凭前 50 桶样本给全局结论 |
| 三维下钻 | 一个维度作为切换条件，另两维图表／表格 | 受控筛选与完整结果分页 | 把三维堆成难读的立体图 |
| 解释追问 | 1–3 张「事实 → 解读 → 待验证」短卡 | 引用上一报告证据；过期需重查 | 无证据继承结论或重复全套仪表盘 |

PV 占比只在分母和完整范围可证实时计算。UV／UIP 可显示各桶独立值，但不宣称各桶占比加起来为 100%。「其他」只能由全量互斥桶在后端聚合，不能把未加载部分或 UNKNOWN 填入「其他」。单点数据用数字／点，不画虚假趋势线。

## 5. Schema 协议分两层

用户所说的 scheme 本方案按 **JSON Schema** 理解。JSON 输出由后端解析、校验和组装，前端只渲染已通过校验的报告模块，不解析模型 Markdown 标题来猜结构。

### A. 模型输出：`CampaignNarrativeV1`

模型负责选择重点、短解释、待验证假设和下一步建议；从后端候选目录选择事实／图表／动作引用。**不让模型重新抄写 PV／UV／UIP、数据序列、分组身份或完成状态。**

Schema 草案：[campaign-narrative-v1.schema.json](campaign-narrative-v1.schema.json)。示例：[campaign-narrative-v1.example.json](campaign-narrative-v1.example.json)。这些文件是设计工件，尚非生产协议。

```json
{
  "schemaVersion": "campaign.narrative.v1",
  "leadFindingId": "finding_1",
  "findings": [{
    "id": "finding_1",
    "kind": "OBSERVATION",
    "claimRef": "claim_peak_day",
    "explanation": "峰值集中在单日，建议结合当日投放记录核查原因。",
    "evidenceRefs": ["evidence_daily"],
    "limitationRefs": []
  }],
  "viewRefs": ["view_daily_trend", "view_link_ranking"],
  "actions": [{
    "actionRef": "action_peak_device_breakdown",
    "rationale": "查看高峰是否集中在某类设备。",
    "evidenceRefs": ["evidence_daily"]
  }]
}
```

`claim_peak_day` 对应的「峰值日期、PV、比较结论」由后端计算和填入显示标题。模型只解释这个已知事实。`HYPOTHESIS` 另有 Schema 分支，必须带待验证假设和后端验证动作引用，不伪装为已证实的 OBSERVATION。自由解释仍可能有语义错误；仅验证引用存在不能证明原因判断为真。

### B. 后端输出：`CampaignReportV1`

| 字段 | 所有者／用途 |
| --- | --- |
| `schemaVersion`, `reportId`, `generatedAt` | 后端生成协议版本、报告身份和时间 |
| `queryState`, `coverage`, `interpretationState` | 后端分别判定执行、数据覆盖和解读是否有效 |
| `scope` | 已授权对象、实际期间、时区、筛选；展示和续问的共同依据 |
| `headline` | 从已验证 lead finding 的后端事实模板生成；受数据限制约束 |
| `metrics` | 绑定指标引用、显示值、单位、比较有效性、口径引用；不来自模型数字 |
| `panels` | 后端选择白名单图表类型／数据集引用／关联 findings；前端决定布局尺寸 |
| `findings` | 已校验观察／明确标记的假设及证据引用 |
| `actions` | 后端白名单动作及参数范围；模型不能提供 URL、代码、SQL 或写操作 |
| `limitations` | 必须呈现的数据缺口及适用模块；后端强制附加，模型不能删除 |
| `evidenceIndex` | 本报告授权范围内的精简证据与审计引用 |
| `datasets` 或授权读取引用 | 真实数据只存一份；图表、卡片、导出都引用它 |

生产版 Report Schema 在模块清单确认后细化为有判别字段的类型，不接受任意 `Map` 或模型自定义 HTML／ECharts option。格式草案和示例与当前 `AgentRunResult` 分开，不能把示例当作已实现 API。

## 6. 后端解析与事实约束

处理顺序：**工具取数与完整性校验 → 事实／证据／视图／动作目录 → 模型 JSON → Schema 校验 → 引用和业务语义校验 → 报告组装 → 前端组件渲染。**

1. JSON 严格解析，拒绝重复 key、尾随额外内容、非有限数字和截断响应；采用字段／类型／枚举白名单。草案使用 `additionalProperties:false`，避免静默接纳任意字段。规范依据：[JSON Schema object](https://json-schema.org/understanding-json-schema/reference/object)。
2. 所有 `claimRef/evidenceRef/viewRef/actionRef` 必须存在于当前报告的服务端目录，属于当前授权范围；`leadFindingId` 唯一且存在，观察必须绑定后端已计算事实。
3. 校验期间可比性、零基期、单位、数据覆盖、快照与采样限制。引用相同不能代替这些校验。图表结果来自工具，模型不提供数列；任何带数字的事实句由模板绑定指标生成。
4. 对自由解释中的新增数字、确定因果、ROI／转化率等无事实支持表达进行拦截或降为「待验证」；自然语言语义检查不能承诺百分百正确，保守降级优先于输出确定结论。原因假设有合法引用也不代表已证实。
5. JSON 格式错误、空响应、截断或引用错误时，保留有效数据图表，使用服务端事实短句，并标注「数据已就绪，解读暂未生成」。V1 不做无限重试；用户可显式重试解读。
6. 图表和导出共用同一个事实来源。Graph 仅保存已压缩证据、短叙述和引用；不把完整 `report/datasets/cards/toolCalls` 各复制一份。新报告组装尽量位于最终传输边界，旧兼容字段从同一事实构建，不再次进入 checkpoint；新轮重置报告派生状态。
7. 向当前共享 `AgentRunResult` 增加投放专用可选报告字段并提供旧构造兼容；安全 Agent 保持原有行为。前端有 report 走新渲染器，无 report 走旧适配；`answer` 由已校验报告生成简短兼容文本，不作为另一份独立事实。

当前 `DeepSeekSpringAiChatModel.requestBody` 没有发送 `response_format`，legacy 适配也未透传。首版建议对投放解释调用显式启用 JSON 输出模式，并始终本地校验完整 Schema。当前使用 Chat Completions；官方文档列出 `json_object`，这不等于本地业务 Schema 已通过。无需为此更换模型供应商或调用协议。参考：[DeepSeek JSON 输出](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)、[当前 Chat Completions 参数](https://api-docs.deepseek.com/api/create-chat-completion/)。

## 7. 状态与空数据也要设计

状态分三个维度：`queryState = NEEDS_INPUT | PENDING | SUCCEEDED | PARTIAL | FAILED`；`coverage = COMPLETE | PARTIAL | UNKNOWN`；`interpretationState = VALID | FALLBACK | NOT_REQUESTED`。前端显示文案由后端规则映射，不由模型自报成功。

| 情况 | 用户看到的内容 |
| --- | --- |
| 缺分组／期间 | 小型澄清卡与选择操作；没有空白指标墙和长篇失败报告 |
| 异步处理中 | 阶段状态、实际范围、查看进度操作；无虚构百分比和数字 |
| 有效零访问 | 明确「该完整期间未记录有效访问」，真实 0；不展示增长率或原因推断 |
| 只有部分结果 | 保留可用卡片，缺失模块明确状态；影响结论的限制放在对应图旁 |
| 全部取数失败 | 简短失败卡与可执行下一步；不显示「完整报告」、假数字或空图 |
| 取数成功、模型失败 | 数据仪表盘和确定性事实保留，解释位置显示轻量降级说明 |
| 完整性未知 | 明确「覆盖范围未确认」，不能当作完整数据或零流量 |

历史和导出使用同一报告快照、状态、范围与口径。常规导出为指标、图表对应的数据表和短结论；诊断 JSON 作为单独选项，不默认塞入正文。快照过期、权限变化或解释追问跨范围时必须重新核验。

## 8. 建议实施顺序与验收

1. 后端事实目录、状态合同、Narrative Schema／解析器、Report 组装器及失败降级。保留旧接口兼容。
2. 新投放报告壳、指标带、主分析卡、辅助卡与短建议；接入现有表格、图表组件及口径问号，按问题选择模板。
3. 统一历史、复制、导出与继续分析；再扩展地域和联合维度切换。

后端合同必须覆盖：合法 JSON、重复 key、额外字段、空／截断响应、伪造引用、跨范围／跨用户引用、零基期、PARTIAL、UNKNOWN、模型失败、Top N／前 50 桶样本限制，以及新旧接口兼容。维持 256 MiB 堆下 Graph 回归，确保新增报告不重新复制大数据。

呈现验收重点：首屏能找到「结论、数字、主图、依据」；卡片解读不出现大段文本；错误不会伪装为完整报告；手机版所有图表说明与操作可达。用户当前限定后端测试，不启动 Docker。方案阶段不运行任何服务；后续前端视觉验收应按届时要求执行，不把未验收内容写成已完成。
