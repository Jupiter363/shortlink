# 仓库结构整理：现状分析与实施计划

日期：2026-09-10。分析基线：`main`，提交 `896e2ceffab926b7986ebbd986738fde12a98b71`。

实施跟踪：入口准备已通过 [PR #7](https://github.com/Jupiter363/shortlink/pull/7) 合入；模块分层、G1–G6 候选验收和本地归档已完成，由 [PR #8](https://github.com/Jupiter363/shortlink/pull/8) 跟踪合并。完整记录见[仓库整理验收](../../integration/repository-layout-2026-09-10/README.md)。以下正文保留最初规划的范围、步骤和门禁，具体完成情况以执行记录为准。

## 1. 结论与优先级

建议将 11 个 Java 模块按用途归入 `services/`、`libraries/`、`jobs/`，保留 `deploy/`、`scripts/`、`doc/`。先明确入口并消除路径假设，再迁移模块，最后单独处理本地残留。

当前模块已具备独立职责，Maven 模块内部基本遵循标准结构。整理的主要收益是让开发者快速区分常驻服务、嵌入式库、Flink 作业和验收工具，降低路径维护成本。目录分层本身不会提高 QPS，也不构成业务架构优化的验收。

需要优先解决的是：

1. 三个 JAR 启动器、三个 Maven 验收入口和两处 Java 测试依赖现有目录位置，必须随迁移闭合。
2. 现行脚本与历史脚本缺少统一导航，两个旧 Agent 脚本的停用状态还不相同。
3. 历史报告绑定源码路径、制品和 SHA，不能通过全局替换让旧报告“适配”新目录。
4. 本地旧模块、构建产物和工具包需要清点，但它们与 Git 里的仓库布局是两个问题。

## 3. 参考了哪些布局，采用哪些原则

参考内容于 2026-09-10 查阅。以下是对项目当前需求的判断，不将外部仓库的目录名称视为统一标准。

| 官方参考 | 观察 | 本仓库采用的原则 |
| --- | --- | --- |
| [Maven 标准目录规范](https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout) | 模块内约定 src/main、src/test、resources 和 target | 完整保留模块内部结构，构建产物仍在各模块 target；不把所有源码合到根 src |
| [Spring Petclinic Microservices](https://github.com/spring-petclinic/spring-petclinic-microservices) | 多个服务仍平铺，另设 scripts、docs、docker，并提供根构建入口 | 平铺本身不属于缺陷；关键是入口明确、源码和运维资料分开，不照搬其部署技术 |
| [Keycloak 根 POM](https://github.com/keycloak/keycloak/blob/main/pom.xml) | 根聚合既有 core 等模块，也有 misc 下的嵌套模块路径 | 目录分组可以与统一 reactor 共存；不用为每个分类目录都添加一层父 POM |

Maven 将聚合和继承分别定义，modules 可以填写相对目录；因此推荐根 POM 直接聚合新的 11 个叶子路径，子 POM 仍继承原根父 POM。[Maven POM 参考](https://maven.apache.org/pom.html)

### 3.1 方案比较

| 方案 | 收益 | 成本 | 结论 |
| --- | --- | --- | --- |
| 保持平铺，仅补导航 | 改动最少，构建路径全保留 | 服务/库/作业仍需逐个辨认 | 可接受的低成本备选 |
| 所有模块归入 `modules/` | 根目录变短 | 仍需处理全部模块路径，分类信息却没有增加 | 不推荐 |
| `services/` + `libraries/` + `jobs/` | 直接表达运行角色和复用关系 | 所有模块加一层，需要联动构建、工具和当前文档 | 推荐；当前 7/3/1 的边界足够明确 |

`jobs/` 目前只有一个模块仍有价值：Flink 作业由 Flink 集群提交执行，与 Spring 常驻 Worker 的交付和生命周期不同。分组后不继续按业务域叠加目录，也不引入新的部署单元。

## 5. 必须一起处理的路径与运行约定

### 5.1 Maven 和模块内测试

- 根 POM 的 11 个 module 改为完整新路径；11 个子 POM 显式添加 `../../pom.xml`，分类目录不新增 POM。
- 坐标、版本、Java 包、主类、依赖图、Boot repackage、Flink Shade、finalName 和资源过滤规则保持。Admin 和 Agent 的无版本 JAR 命名不能被顺手统一。
- Maven 选择器优先使用唯一 artifactId。例如根目录执行 `mvn -pl :shortlink-command -am test`；Admin 使用 `:shortlink-admin`，Gateway 使用 `:shortlink-gateway`，Agent 使用 `:shortlink-agent-service`。`-pl` 支持坐标或相对路径，[Maven CLI 参考](https://maven.apache.org/ref/3.9.9/maven-embedder/cli.html)；`-am` 用于同时构建 reactor 内依赖，[多模块指南](https://maven.apache.org/guides/mini/guide-multiple-modules.html)。
- 两处读取根目录 SQL/脚本的 Java 测试改为明确且受限的仓库根定位，校验根 POM 身份和目标存在。从根目录与新叶子模块目录运行都应定位同一文件；不复制 SQL 到第二处，也不向上找到任意同名文件就算成功。
- `.git` 可能在 worktree 中是文件，也可能在源码导出中不存在，不能只用“存在 .git 目录”识别根。

### 5.2 脚本和候选构建

三个 JAR 启动器修改制品路径时，保留现有逻辑服务键、文件名、参数和输出结构。可各自使用短小的显式路径映射；不为三处路径引入跨 Python/PowerShell 的新工具框架。

三份 PowerShell 集成入口同步 `-pl`，并明确 Java/Maven 参数与隔离前提。选择含 reactor 内依赖的模块时必须带 `-am`，尤其补齐现有 gateway/redirect 入口；`clean package` 不会安装公共库，后续独立入口不能借 `.m2` 中旧 SNAPSHOT 满足依赖。当前写死的本机 Java 默认位置改为参数或 `JAVA_HOME`，入口缺失时及时报错；测试库授权和重置保护保持。

新候选构建包含根 POM、services、libraries、jobs、scripts、deploy 和所需文档，候选根仍是整个仓库根。保留 source-root 与 harness-root 的语义，不把 source-root 改成 services；不向旧 `.work` 候选覆盖新源码，不复用旧 target 作为新制品。

候选路径同时考虑 Windows/WSL 的路径表达、文件名大小写和新增层级后的最长路径。入口应支持当前中文仓库路径；必要时用短路径候选构建，不通过重命名 Java 包或修改旧证据里的机器路径解决工具限制。

脚本导航逐项说明用途、支持环境、前提、是否启动资源、产出位置、当前/历史/停用状态。两份旧 Agent 脚本本轮保留路径；技术退役仍可执行的 risk 脚本需要独立变更并处理其契约测试，不在目录移动中隐式改变行为。

`scripts/performance/` 的实现与 test 文件先保持同目录。后续只有维护规模确实需要时，才单独规划 Python 导入、动态加载、workload 路径和源码身份迁移。

### 5.3 部署与配置

`deploy/` 不迁移，因此现有 Compose 相对挂载、APISIX Lua 包路径、模板渲染器和监控文件保持位置。静态审计未发现受管 Dockerfile 或 Compose build context；不为目录整理新增业务容器化方案。

更新 `deploy/README.md` 中仓库内 JAR 路径和 Leaf 来源链接，区分“仓库构建产物路径”与“交付到服务器后的 JAR 文件名”。保留生产 properties 的 classpath 参数，服务端口、Kafka Topic、Flink UID、数据库 schema、限流参数和线程预算不随目录变化。

被忽略的本地 YAML/环境文件只清点位置，不输出凭据、不加入 Git，也不为了迁移放宽 POM 的资源排除。已受管的 production properties 和部署模板继续作为配置约定来源，避免另造一套重复配置。

## 6. 文档、上游源码和证据如何归纳

| 类型 | 处理方式 |
| --- | --- |
| 根 README | 保留原章节、功能介绍和 `doc/images/shortlink-global-architecture.png`；仅更新目录树、当前命令和链接 |
| 当前使用文档 | root/deploy README、模块 README、doc/analytics、当前 integration 指南逐个核对路径；特别更新 id-generator README 的两条 `-pl` 命令 |
| 开发导航 | 新增 `scripts/README.md` 和 `doc/development/repository-layout.md`，从 doc 总入口可达；指南解释现行位置，本计划保留决策过程 |
| 历史重构计划/压测过程报告 | 保留原始上下文；需要说明新位置时在当前索引增加迁移说明，不全局替换历史正文 |
| 原始 JSON、源码快照、SHA 清单、合并验收收据 | 内容与路径保持原状；FAIL 和限制条件同样保留，不改写为新布局验收结果 |
| Leaf 上游资料 | `id-generator` 连同 UPSTREAM、LICENSE、patches、upstream 快照整体移动；上游源码和许可证原始字节不变，清单中的上游路径不改成仓库新路径 |
| 本地 `.work` | 原候选和运行记录保留；新的验证创建独立批次，不污染旧批次或写回旧 SHA |

正式迁移时新增记录，包含：`oldPath → newPath`、变更前后提交、原始字节 SHA-256、是否修改内容及原因。内容没变的文件可证明搬迁前后相同；POM/脚本等确有修改的文件单独列明。历史报告仍只证明历史提交和配置，不能据此宣称新布局已完成相同压测。

保留 `doc/.gitattributes` 的字节保护。检查复制/搬迁时的 CRLF/LF 和编码差异；不能用规范化后的哈希替代原始字节身份。旧代码链接通过原提交和迁移映射追溯，不用根目录软链接或空壳旧模块长期遮蔽遗漏。

## 7. 分阶段实施与 PR 拆分

后续通过一个跟踪 Issue 与两个依次合入的 PR 执行，使用 `codex/repository-layout-*` 分支。每个 PR 都必须保持当时布局可构建、可运行；不先合入破坏路径的移动，再用后续 PR 修复。

| 阶段 | 具体交付与拥有路径 | 验收/退出条件 | 对应提交边界 |
| --- | --- | --- | --- |
| R0 基线冻结 | 记录 HEAD、受管清单、11 模块/制品映射、未跟踪与忽略文件清单；证据写入新 `.work` 批次 | 工作树已有改动有归属；原图、历史证据、上游快照身份已记录 | 实施前准备，不移动用户文件 |
| R1 入口准备 | scripts README、doc/development 导航；3 个 Maven 入口使用稳定选择器；2 处 Java 定位兼容根和叶子深度；梳理 Java 路径参数 | 旧布局仍可用；定位测试从不同 cwd 指向同一目标；脚本分类准确 | PR 1：入口与路径准备 |
| R2 模块迁移 | 11 模块移动，根/子 POM 联动，3 个 JAR 启动器路径联动，README/deploy/模块指南更新 | 全部改动在同一候选中闭合；业务合同、制品名、当前架构图不变 | PR 2：原子目录迁移，验收通过后才合入 |
| R3 候选验收 | 使用新布局干净副本，完成下节门禁；生成迁移映射和验收记录到 doc/integration 新批次 | 不借用旧目录产物；真实执行、跳过和未测范围明确 | 随 PR 2 提交，不将缺失验收后置 |
| R4 本地归档 | 单独列 project/aggregation、日志、工具包等清单及恢复位置 | 仅处理确认用途的本地残留；原始证据与私有配置可恢复 | 本地操作，独立于 Git 迁移完成状态 |

R1 和 R2 顺序执行。并行协作时可分别负责 POM/Java、脚本、当前文档的审计或限定修改，根 POM、迁移清单和最终集成由同一整合者负责；共享文件不并行写。

不把引入 Maven Wrapper、完整 CI/CD、统一格式化、依赖升级或旧 Agent E2E 重建捆绑到这两个 PR。路径门禁稳定后，可以另行把它接入 CI，避免今后继续引入本机路径依赖。

## 9. 本地残留、回退与范围边界

本地清理先逐项记录路径、文件数量、用途、是否仍被进程引用及恢复位置。旧模块目录里可能保留未纳管配置，不能因 POM 已移除模块就连目录递归删除。`.work` 含原始测试证据，也不作为普通缓存一键清空。先将确定的残留归档到明确的本地位置，验证可恢复，再决定是否删除；不把私有归档塞进 doc 或 Git。

Windows 上任何后续递归移动/删除，先解析完整源/目标并核对边界，使用 PowerShell 原生 LiteralPath 操作，禁止无范围的 `git clean -fdx`。若没有运行资源冲突，目录分析本身无需停止服务或释放线程。

已合入的 Git 迁移通过对应 PR 的 revert 回退，根 POM、模块路径和启动器作为整体回退；本地私有文件依独立清单恢复，不能认为 Git revert 会恢复忽略文件。每个 PR 保留可复核的基线提交。

本计划范围只覆盖仓库组织、路径可靠性、导航和搬迁验收。服务合并/拆分、号段算法、网关调度、Kafka 并行度、统计协议、Agent 授权或 checkpoint 行为等业务问题另立任务，不混入目录整理。
