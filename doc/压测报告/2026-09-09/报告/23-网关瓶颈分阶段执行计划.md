# 网关瓶颈分阶段执行计划

日期：2026-09-09。依据[归因复核报告22](22-硬件边界与架构实现瓶颈归因复核.md)，按用户授权先规划，再依序执行。当前重构分支上的历史改动保留。本轮工作目录为 `.work/gateway-execution-20260909/`，每次实验使用新ID和独立结果，最终回填本文件的执行记录。

## 目标与验收口径

依次解决接入调度、节点发送并行度/攒批、被证实的编码热点，最后测可持续吞吐平台并判断硬件约束。没有证据的候选不进入产品代码；已被反证的方案记录原因后转下一项，不重复盲调。

先使用APISIX→固定302桩+私有Kafka隔离网关成本；组件诊断完成后，必须恢复APISIX→真实Redirect→缓存/数据库的跳转链路验收，才能回答用户要求的跳转QPS。组件结果仅用于归因，不能替代业务验收。Agent不参与本轮。

所有候选保留独立事件、正确302和目标地址、不重试HTTP、Kafka确认后计delivered、重试/失败可见、有界在途预算和最终排空。HTTP及scheduled-to-completion P99沿用≤80ms；未发请求、错误、拒绝分别报告，不能以移除统计或丢弃首秒获得通过。

## 阶段0：冻结环境和观测准备

- 保存源文件SHA、Git状态、实时CPU/core/SMT拓扑、WSL/宿主约束、容器cpuset/配额/内存和版本。相同实验中的服务与发生器CPU范围固定；基准复现沿用旧cpuset，拓扑调整单独作为变量。
- 只使用WSL `shortlink-refactor-it`及其专用Docker socket；本轮拥有的容器/PID明确登记，历史依赖保持停止。完成后停止本轮资源，保留证据及历史数据。
- 补发生器每次丢弃的时刻/原因/源池和全局占用，以及owner归还槽位边界；默认负载行为不变。实现有界事件循环延迟探针，能力探测后选用按目标PID限定的原生取证。
- 先完成新增诊断工具的单元/真实运行时smoke验证，确认计数不受诊断截断影响、覆盖缺失显式呈现，再发压。

## 阶段1：定位并修复接入调度

**要回答：**新连接已经发出请求后，为何迟迟未进入HTTP处理；是accept/首次read延迟、worker持续占CPU、线程没被调度，还是发生器供给限制。

1. 固定1 worker和旧资源，复现短冷连接实验；逐请求关联dial/write、accept/首次read可用边界、HTTP时长、5ms事件循环延迟及原生on/off-CPU。取证不可用时明确缺失，使用独立边界时间或受控对照补证，不能以缓存毫秒时钟充当内核时间。
2. 固定相同连接数/源地址/速率，比较冷连接与完整业务预热后场景。预热请求计入事件账本；保留冷接入门槛。再次单独验证发生器每源槽是否限制输入。
3. 根据结果只修实际原因：可能涉及公平接入/连续工作预算、业务就绪条件、具体阻塞调用或发生器测量缺陷。发生器修正必须与产品收益分开。multi_accept不直接默认开启，先前副作用必须覆盖。
4. 同资源、同时长复测修复前后；核对首连接分布、复用P99、每秒完成、drop、ACK/offset、队列年龄与排空。新连接改善而复用/投递退化则不采纳。

**阶段完成条件：**有边界证据解释原失败；修复有对应回归和对照收益，或确认该约束应由后续发送组织/编码阶段处理并记录因果。不能仅以“worker100%”结束定位。

## 阶段2：优化节点发送并行度和攒批

- 固定阶段1结果、4 worker、节点队列总量和CPU；先比较每worker发送槽4、2、1，对应节点16、8、4槽，其余参数相同。
- 按结果选择发送槽后，再独立比较linger 1ms与较长但仍在当前允许范围内的值。batch32为上限，不能将配置值当实际批量。
- 核对Produce/事件、实际批量分布、Kafka与网关CPU、ACK尾延迟、最老事件年龄和队列拒绝；更少RPC必须同时维持HTTP与交付合同。
- 将胜出的配置和节点预算语义落实到部署、性能入口、文档与测试。若没有收益，保留原配置，并以观测决定是否需要独立聚合进程；不为了追求批量强行堆积。

**阶段完成条件：**可重复对照得到有效配置，或明确当前批量组织的约束及下一步架构必要性；没有收益的参数不合入。

## 阶段3：按热点削减编码和记账成本

- 在阶段2固定配置下补足原生热点。优先检查完整worker账本反复编码、身份字段构造、事件JSON和Kafka协议编码，区分累计CPU与单次长阻塞。
- 只改已被数据支持的成本；保持当前账本原子一致性、worker generation、崩溃残留及最终排空可见性。紧凑表示/复用结构优先于降低发布频率。
- 如果降低发布频率必须增加明确的revision/dirty、最大滞后和静默flush合同；不得把未发布状态误报为0 pending。
- 跑相关Lua/Python回归、真实Kafka有限集成，随后同负载复测；收益不足或观测语义退化时撤回本轮候选。

**阶段完成条件：**热点成本被降低且合同完整，或已有充分证据说明这部分并非优先成本，记录不修改的依据。

## 阶段4：测稳定平台，再判断是否扩容

- 固定最终代码、物理CPU映射、消息配置和发生器；冷连接与预热后的持续流量分别验收。
- 从已跟上的6000/s开始递增输入，出现持续平台、P99超限、持续队列增长或错误时停止升档，向下确认边界；不能将输入上限当系统上限。
- 候选稳定档至少60秒并重复3次；记录窗口内完成吞吐、双P99、drop、每秒事件交付、队列年龄、CPU/调度与IO。预热和尾部排空单独记账，不提前计入QPS。
- 若组件通过而真实业务链路未覆盖，只报告组件容量；恢复真实Redirect验证后才能报告该业务范围的结果，Agent仍排除。
- 硬件判断依据同窗实际资源饱和及受控扩资源收益；优先排除发生器、串行执行和小RPC放大。明确单进程限制、分配资源限制与共享宿主限制。

执行补充：20,000/s 阶梯出现网关队列拒绝后，先完成 8,000/s 的 60秒×3，再做两组相同 30 秒预热、5 秒正式的 CPU 对照。对照组网关 CPU 0–3、Kafka 10–11；扩资源组仅将网关改为 0–3,8–9，Kafka 仍为 10–11。两组均固定 4 worker、每 worker 1 sender、5ms 攒批、节点1000条/8MiB及2048发生器owner；桩4–5、观察6–7、发生器12–15保持。先做独立对照组，是因为原阶梯 Kafka 使用8–11，不能把原组直接当作单变量 CPU 对照。五秒结果只用于资源增益与归因，不能替代三轮持续容量。

两组各计划401,500条。三轮稳定窗口后按预计已确认5,358,704条、新对照最多401,500条和末轮完整三倍预留1,204,500条，合计6,964,704条，仍满足本轮7,000,000条预算；各轮继续核实际结算、磁盘与预留，不扩大历史模型上限。

**最终交付：**代码/配置及回归结果、保留失败的对照报告、稳定档或尚未通过的明确边界、硬件是否需要扩容的证据、资源停止记录。

## 数据与资源预算

继续累计历史已确认的33,504,534条Kafka记录；不删除数据重置计数。前轮128GiB模型剩余49,898条不足以进行有意义的持续验证。本轮初定新增3,000,000条；完成短对照后，按60秒×3及每轮完整3倍最坏重试预留重新核算，将本轮新增上限调整为5,000,000条实际Kafka记录（按4096B/条约19.07GiB）。历史模型上限仍为160GiB/4096B，即41,943,040条，没有再次提高；历史加本轮上限为38,504,534条，仍在该模型内。预算调整是测试规划，不是broker扩容或实测容量结论。

每个实验开始前重新核对两个相关文件系统的实际可用空间、已确认记录和最坏重试预留；至少保留25GiB或总空间15%中的较大者，另留本实验完整预留。压力记录按最多3倍计划事件预留，实际offset与排空核实后结算。若无法满足则降低/停止该实验，不能静默越界或删除历史。诊断工具输出也有明确上限。持续窗口所需预算优先保留，避免所有预算消耗在短对照上。

进入最终阶梯前，已新增1,077,165条实际记录。为保留超过10,000/s的短阶梯，以及最终60秒×3每轮完整的3倍重试预留，本轮实际记录上限最终调整为7,000,000；历史加本轮为40,504,534条，仍低于既定41,943,040条/160GiB模型上限。实际可用磁盘检查和每轮最坏预留不变。新增发生器克隆允许最高20,000/s，但单轮预热加正式到达总数限制在1,000,000之内，防止超过逐请求诊断完整覆盖范围；发生器自身上限不能当作网关容量上限。

### 首轮冷/暖对照发现

本段是执行中的失败记录，不代表稳定容量通过。证据在 `.work/gateway-execution-20260909/experiments/`。

- `cold-loop-1`：1 worker、节点4发送槽、linger 1ms、6000/s×3s。18,000次计划到达中14,338次正确HTTP且全部ACK/落Kafka，3,662次未发（3,659 SOURCE_BUSY、3 WORKER_LATE）。HTTP P99约2,959ms；loop最大迟到40.10ms，未出现持续3秒的整个事件循环停顿。单条首次连接写完至Nginx缓存计时起点残差约2,960ms，需进一步用实际accept/read定位。
- `warm-1`：同配置增加30秒从100/s升至6000/s的业务预热，再测3秒。全部512首次连接在1.845秒内完成，正式窗没有fresh请求污染；正式到达中15,849次正确HTTP、2,151 SOURCE_BUSY，P99 109.63ms。按正式窗实际完成计算为5,288 QPS（包含少量预热跨窗完成）。正式窗内部2.925s的CPU差分：edge 99.76%、Kafka 5.65%、stub 40.87%，均未触发CPU配额限流。
- 暖组总HTTP/attempted 105,163，ACK/实际Kafka 85,307，另19,856条明确被 `queue_count` 拒绝；拒绝统计覆盖整个预热及正式窗。它是实际统计事件损失，不能因HTTP成功而验收，也不能说成Kafka消费能力不足。
- 暖组首次日志抓取在停止前发生超时，原失败与残缺日志保留；随后从同一已停止容器读取新 `edge-recovered.log`，以CID/runId/SHA绑定，105,163条客户端与服务端记录全部唯一匹配。修正后续runner为先停止再取最终日志，并补严格身份、覆盖和逐请求关联门禁。

### 接入与发送组织中间结论

- `cold-kernel-1`：完整内核取证无丢事件。后2秒worker on-CPU 99.888%；正式3秒253次HTTP accept对应253次epoll返回，逐次只接一条。能可靠关联的请求中，写完到accept的等待下界P99为2592.44ms。这不是线程始终未获调度。
- `accept-kernel-1`：multi_accept使512条连接更快被接收，但接受后首次read P99升至121.82ms，12,416个正确HTTP只有6,996条ACK/Kafka，另5,420条队列拒绝；该候选不采纳。一次大量接入把排队转移到了处理和投递。
- 固定4 worker、6,000/s、30秒业务预热+5秒测量，三种发送槽配置及linger5配置每组均121,500个正确HTTP=ACK=Kafka，没有drop或事件拒绝。1槽/worker、linger1→5ms，Produce 68,166→19,570，平均每次Produce 1.782→6.208条；正式窗edge CPU 209.49%→160.18%、Kafka 72.61%→24.57%，HTTP P99 1.972→0.938ms。单组短对照不是持续容量承诺。
- `fd-baseline4-kernel`使用4 worker和低事件量的accept-only新采集器，75,202条事件、lost=0、malformed=0。每worker均在accept4返回FD64、128时出现20.810–59.219ms的D等待。该模式不采read，不能将它用于accept→read结论。
- 发生器另外出现fresh连接累计62/126/252附近的全局派发/归还停顿；原生Go socket使用RawSyscall，可能在FD表扩容等待期间占住Go调度P。新发生器显式选择仅预分配FD表，仍保留512条冷HTTP连接；完整Go测试38顶层+46子测试通过。后续对照必须将测量工具收益与网关代码收益分别报告。
- 组件试验的节点预算为1000条/8MiB；正式部署及supervisor的目标节点预算为2000条/16MiB，二者不可混算。默认部署未固定worker导致配额随auto放大，是需要同步修复的配置确定性缺口。
