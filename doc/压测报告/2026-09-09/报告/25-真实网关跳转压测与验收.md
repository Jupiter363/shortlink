# 真实网关跳转压测与验收

日期：2026-09-09。状态：12阶段压测已完成，真实热点跳转5,000 QPS通过三轮60秒验证；提高客户端并发后的6,000 QPS单轮通过。证据目录：`.work/real-gateway-qps-20260909/`；本次真实部署的数据和阶段输出在 `.work/performance/20260909T064903Z-5cdd318d/`。

## 业务路径

压测器 → APISIX真实跳转路由（保留边界校验、limit-req、limit-conn、访问日志与边缘事件）→ 真实Redirect JAR → Caffeine L1 / Redis L2 / 必要时JDBC回源 → 链接状态、有效期与风控校验 → 原始URL的302。

通过真实创建API生成10个主短码，每个返回的Location必须与其创建时的原始URL相同，不跟随访问外部目标。真实热缓存请求可命中L1，不声称每次必访问Redis；1秒权威租约与200/s回源预算保持不变。本轮是热点跳转场景，不能套用到大量随机冷短码。

每个成功GET分别产生点击、Redirect结果与网关EDGE三路事件。保留真实Kafka投递，前后核对每路attempted/delivered/rejected/failed/pending及真实topic offset。Agent、Analytics聚合查询不加入本轮；跳转业务真实执行与统计投递到Kafka的验收范围明确区分。

## 顺序与配置

1. 构建当前四个服务JAR，恢复专用WSL测试依赖；创建新schema并选择空的专用Redis DB，不清理历史数据。
2. 以4个APISIX worker、每worker 1个sender、5ms攒批、节点2000条/16MiB队列运行。Java每进程Xmx384MiB、ActiveProcessorCount=2；实际cpuset、依赖内存限制、JAR与插件SHA均冻结。HTTP入口，不含TLS。
3. 先做真实创建与跳转路径冒烟，核对Location及当前进程身份，再做64来源验证。所有正式压力只请求本次APISIX，不改成直连或固定302服务。
4. 从低档开始逐档递增。短档用于找到通过/失败区间，出现错误、事件拒绝或持续积压停止升档；通过档再做60秒持续验证，重复结果分别保留。发生器未发和客户端饱和独立报告，不当作服务端极限。
5. 逐档报告目标输入、正式窗实际正确302吞吐、HTTP及含调度等待P99、未发/错误、三路投递与积压、CPU/内存/GC及Redis观测。P99门槛沿用80ms，零未发、零错误、零事件拒绝/失败。预热和排空不计入正式QPS。

本次部署为 `20260909T064903Z-5cdd318d`，具体资源如下；CPU编号均为同一WSL实例中的逻辑CPU编号，并非独立物理机器。

## 资源与结束条件

仅使用WSL `shortlink-refactor-it` 的专用Docker socket。每轮按最多100万HTTP请求约束，按每GET三条事件及三倍重试预留检查实际磁盘，至少保留25GiB；记录原始Kafka累计offset，不能用新run重置历史消耗。阶段及本轮资源均登记身份，结束后停止所启动服务和依赖并恢复原依赖CPU范围，保留数据、失败及成功证据。

本轮最初按1000万条新增Kafka记录含最坏预留控制。6k第二轮持续测试出现421次SOURCE_BUSY未发、HTTP P99 88.62ms，不能签收6k稳定容量，因此转为5k三轮确认。保留同一baseline和所有失败，已发生5,913,853条；计划再新增3,388,500条，最后一轮包含三倍重试时累计预留上界为11,561,353条。按实际磁盘重新核验后，将本轮预留上限调为1500万；原manifest/runtime identity归档为v1，stage-v2仅改变预算上限，17项纯测试及逐字节单行diff确认HTTP、延迟、未发、三路统计、单轮请求和磁盘门槛均未放宽。产品代码、制品和资源配置没有变化。

### 已暴露的边界

- 8k拒绝直接归因为APISIX `queue_count`。触发采样中一个worker已达500/500条，节点合计1887/2000条，而字节预算仅约1.17MB/16MiB；当时4个sender活动，最老事件约259ms。这证明网关局部队列发生接纳失败，不证明Kafka下游消费者或broker硬件已经到上限。Java点击和结果两路完成投递，EDGE缺少338条，整体统计完整性失败。
- 6k第二轮的421个请求因对应来源没有可用执行槽而未发出（SOURCE_BUSY）；发生器按来源分配执行槽，不能由这个原因码断言每次未发时全局1,024槽全部占满。HTTP P99为88.62ms，含调度等待P99为89.91ms，最大HTTP耗时377.51ms。已发的451,079个请求全部正确，三路各ACK 451,079条，Kafka共1,353,237条，不应把该轮失败写成Kafka丢消息。
- 只把客户端槽从1,024增至2,048的最后一轮6k对照通过，对应64个来源各自的槽数从16增至32；服务端制品、CPU、队列与发送参数均不变。正式窗实际6,000.15 QPS，HTTP/含调度等待P99分别11.11/11.27ms，最大HTTP耗时132.66ms；含预热451,500个请求全部正确，零未发/取消/错误，Kafka新增1,354,500条并排空。它说明扩大客户端执行槽后的这次运行可通过6k；由于只做一次、前序运行也有波动，不能证明槽数是全部改善的因果，也不能改写原失败或宣称6k已重复稳定通过。
- 7k只有一次窗口末端未发，原始FAIL保留。该轮观察到约7k正确302吞吐，不能称为已重复通过的7k稳定容量；也不能据此断言应用最高只能处理5k。
- 7k正式窗口内部52.93秒样本中，APISIX约246.75%、Redirect约226.62% CPU；6k首轮内部55.19秒约255.02%和222.99%。100%代表一个逻辑CPU，各进程CPU范围重叠。6k反而出现更高长尾，结果存在运行时波动；这些采样不能证明整机硬件已满。
- Redirect在上述两个内部样本段GC累计暂停分别约0.639s/0.768s，分配约260.7/225.1MiB/s，可作为以后分配热点排查依据，不能直接认定GC是吞吐瓶颈。本轮没有Kafka进程CPU采样，不能声称broker CPU已满。10秒探索档大多不足两个正式窗口内有效采样点，不计算其稳态CPU/GC差值。

### 证据与验收范围

`edge-path-verification.json`的12项路径验证通过，64个真实TCP来源验证通过；每档访问日志再次核对来源。当前四个服务JAR成功重建并校验SHA，真实创建API生成267条fixture，正式压力只做10个主短码的GET跳转。构建本轮未重新运行完整项目单元/集成测试；新runner的纯逻辑测试14项通过、仅预算调整后的v2共17项通过，摘要统计器6项测试通过。

各档 `result.json` 及 `kafka-before.json` / `kafka-after.json` 保留正式时窗、HTTP计数、Location一致性、失败原因、三路ACK/拒绝/失败/排空、Kafka各topic/partition边界、来源日志验证和运行制品身份。高档失败原始数据保留；文档24的固定302组件数字不作为本轮业务基线或验收结果。Kafka验证到原始事件broker ACK及offset守恒，本轮未测Agent、Analytics/Flink/ClickHouse消费聚合，也未测试公网、TLS和大量随机冷短码。

数据库权威查询也有实测证据：`before-load-cache-proof.json` 与 `after-all-cache-proof.json` 中，本轮schema按 `domain_norm + short_uri` 查询 `t_link_route` 的相同SQL digest计数从2增至16,371，实际增加16,369次。它证明压测期间运行真实查址与回源；不是固定302。Redis累计commandstats包含路由以外的策略/风控操作，不据此计算L2命中率。采样在压力窗口外执行，1秒租约过期后路由value key数为0，不能解释为未使用Redis。

最终 `final-boundary.json` 核对267条链接/路由/配额一致、无重复短码和路由缺失、配额预留为0，三路事件队列已排空。完整12阶段汇总为 `summary-final.json`，其中9阶段PASS、3阶段FAIL；失败阶段继续计入累计Kafka和磁盘预算。

`campaign-audit.json` 从12阶段的真实Kafka前后边界独立重算，并与原始baseline到final核对：全轮正确HTTP为3,552,397次，click.raw新增3,552,397条、gateway.request新增7,104,456条，合计10,656,853条，其余topic增量为0。总数等于 `3 × 3,552,397 − 338`，所有阶段的实际增量之和完全相等。8k档原始 `result.kafkaConservation` 和摘要 `kafka` 为null表示其完整性验收未通过，不表示没有产生数据；实际增量483,619条已由该档 `kafka-before/after` 算入累计。核账一致不能消除338条统计拒绝，三项失败判定仍保留。
