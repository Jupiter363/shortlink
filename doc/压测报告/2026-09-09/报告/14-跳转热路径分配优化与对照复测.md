# 跳转热路径分配优化与对照复测

2026-09-08。本轮减少跳转请求内重复的 IP 解析、正则编译和 HMAC 计算，保留代理信任、租户隔离、路由与策略时间边界校验。相同资源下，旧 Redirect 的 5000/s 短档失败，候选短档通过，P99 从 137ms 降至 31ms，进程分配量摊销下降约 59.65%。随后 300 秒确认在正式期 50.924 秒触发 Redirect 事件拒绝保护停止，**持续 5000/s 尚未通过**。本轮压测已停止，资源已释放。

## 实现变化

- `IpAddresses` 的 IPv4 校验改为有界 ASCII 扫描，消除 split、逐段正则及重复 JDK 解析；IPv6 保留字符白名单及原 JDK 规范化行为。
- `TrustedProxyResolver` 复用已解析地址的字节，CIDR 按完整字节与尾部掩码比较。仍从实际 peer 向左遍历，保留 1024 字符、20 跳上限和首个不可信 hop 的停止规则。
- `RedirectController` 预编译短码和访客 ID 正则，复用无状态 HostNormalizer；租户/IP 风险哈希仅在同一次请求内计算一次。Context 每次订阅独立，异步限流后仍重新取时并复验路由和最终策略，不缓存允许结果。
- `RiskHash` 保持 HMAC-SHA256、租户隔离、三个大端长度前缀和前 128 位输出，改用单个有界载荷数组；Mac 仍每次调用独立，不引入共享可变密码对象。
- 压测脚本复用固定标签和请求参数，记录原生整次迭代耗时、场景时间锚及父进程启动时间边界。未配置 GOMAXPROCS 时显式记录未知，不能把 CPU 亲和范围当成实际运行时配置。
- supervisor 增加 `--edge-send-concurrency {1,2,4}`，默认 4，25 项离线测试覆盖渲染和预算。本轮实际两组均使用 4；1/2 槽的容量尚未测量。

生产源码：[RedirectController](../../../../shortlink-redirect/src/main/java/com/jupiter/shortlink/redirect/web/RedirectController.java)、[IpAddresses](../../../../risk-core/src/main/java/com/jupiter/shortlink/risk/IpAddresses.java)、[TrustedProxyResolver](../../../../risk-core/src/main/java/com/jupiter/shortlink/risk/TrustedProxyResolver.java)、[RiskHash](../../../../risk-core/src/main/java/com/jupiter/shortlink/risk/RiskHash.java)。

## 新暴露的限制与后续突破点

长档明确触发的是 [AsyncKafkaPublisher](../../../../shortlink-redirect/src/main/java/com/jupiter/shortlink/redirect/event/AsyncKafkaPublisher.java:152) 的本地事件接纳拒绝。click/result 各自独立 Lane、KafkaProducer、1000 条预约槽和 8MiB 应用字节预算；预约覆盖排队和等待 ACK，最终回调后释放。每个 KafkaProducer 另有 8MiB 缓冲，应用字节预算不是整条通道的总内存上限。网关没有新增拒绝／失败，Kafka 发布 failed 也没有增长。

现有 rejected 指标合并了关闭、事件过大、预约槽不足、字节不足和入队失败。首次非零 quality 采样在 16:25:20.212 UTC，前一采样 16:25:15.212 仍为 0；该失败采样 pending 仅 click54/result19，全部离散采样峰值 click54/result106，无法证明或排除两次采样间瞬时满槽。现有证据缺少 Kafka 客户端 ACK、buffer 等指标，尚不能进一步认定 broker 满、单个发送 worker 饱和或消费链路成为瓶颈。

下一轮应先拆分拒绝原因、记录排队及 ACK 持有时间、pending 峰值和 Kafka 客户端发送／缓冲指标，再分别评估预约持有、Lane 锁竞争和发送效率。现有 `offer` 在同步锁内计算 UTF-8 字节长度，ACK 的终态回调也竞争同一把锁；将编码移出临界区是可验证的候选优化，目前尚无锁等待实证。所有优化仍应保留总条数／字节上界、最终 ACK 后释放、失败与重复事件对账；单纯提高队列上限不能证明持续处理能力已改善。本轮未修改该发布器，避免把未经同组测试的代码与当前成绩绑定。

本轮验证短链接创建夹具、直连跳转和网关跳转及 Kafka 生产者事件账本。Agent、Flink、ClickHouse 和统计消费能力未参与压测，未证明端到端统计持续吞吐。压测未探索高于 5000/s 的档位，绝对 QPS 上限仍未确定。后续更高档测试应先分离发生器与服务资源，再以新预算核验吞吐及队列增长；当前证据不支持将 Kafka broker 简单认定为唯一瓶颈。
