# 接口与网关跳转压测计划

日期：2026-09-06，执行至2026-09-07；分支：`codex/production-refactor-v07`。状态：**首轮诊断结束，路由证明过期与Outbox积压触发停止条件，高负载和长时容量未签收**。已执行23个阶段及500条真实批次跨号段验证；结果与未执行范围见 [首轮压测报告](07-首轮压测报告.md)。本轮证据：`.work/performance/20260906T151359Z-4f3e05aa/`。

执行顺序固定为：**先测业务接口与 Redirect 直连，定位服务本身的瓶颈；再以相同数据和负载经 APISIX 压测跳转，测量公开入口的可靠容量及额外开销。** 10 万集群跳转 QPS 继续作为规划假设，不预设本机必须达到该数字。

已有基线是 [创建跳转 E2E 验收](05-创建跳转E2E验收.md)：16 个业务用例、14 个网关用例及 HEAD 原始消息核对通过。本文件细化 M6 的第一轮性能验证，不代表完整 M6、Agent 或首次上线容量验收。

## 1. 本轮范围与比较方式

| 阶段 | 实际路径 | 测量目的 |
| --- | --- | --- |
| A：创建接口 | 压测机 → Admin `8002` → Command `8001` → MySQL / Redis / Outbox | 测完整持久化创建和后台适配开销，保留内部认证及当前主体授权 |
| A：跳转接口 | 压测机 → Redirect `8003` → 缓存 / 路由与策略权威 → Kafka | 测 Redirect 单实例基线，包含风控和异步事件生产 |
| B：网关跳转 | 压测机 → APISIX `19080` → Redirect `8003` → 同样依赖 | 测网关路由、边界插件、漏桶、并发保护和边缘事件采集后的容量 |

**公开跳转经过 APISIX，当前不经过 Java Gateway。** Java Gateway 的 64 槽位保护约束管理请求，不应套在跳转吞吐上。完整公开创建路径 `APISIX → Java Gateway → Admin → Command` 可作后续对照，本轮 A 的结果只标记为内部业务接口容量。

Agent、LLM、统计查询、Flink / ClickHouse 聚合压力、批量文件导入、依赖故障注入、多实例 N-1 暂不加入第一轮。Kafka 真实生产保持开启；本轮只评估业务响应和生产者到 Kafka 的稳定性，不声称验证了统计消费能力。

## 2. 开始前冻结环境

当前只读盘点：宿主为 Ryzen 7 5800H、16 个逻辑处理器、约 31.9 GiB 内存；工作盘可用约 265 GiB。尚未固定 WSL 实际资源、磁盘位置和压测机配额，因此这些宿主规格不能直接当作服务配置。

| 准备项 | 执行要求 |
| --- | --- |
| 制品与版本 | 记录 Git HEAD、未提交差异摘要、JAR SHA-256、JDK / APISIX / Redis / MySQL / Kafka / k6 版本；不能只记录分支名 |
| 资源 | 第一轮可复用独立 WSL 做本机诊断。固定 WSL 可用 CPU / 内存、每个 Java 进程 Xms/Xmx、ActiveProcessorCount、依赖限制、磁盘位置和连接池；A/B 比较期间不变 |
| 压测端 | 优先独立机器；本机起步时将压测进程与服务分开分配 CPU 预算，并记录争用。若客户端发不满或 CPU 饱和，先解决发生器瓶颈，不能报告为服务极限 |
| 测试数据 | 使用新建的专用 schema、Redis 独立实例或本次专用空 DB、独立域名和运行标识；不复用开发 `link` 库、不清空既有数据 |
| Kafka | 固定分区 / RF / minISR / 保留期，记录原始消息大小及预计磁盘增量；当前组件夹具的两分区、RF1 只能支持该拓扑的诊断结论 |
| 日志与观测 | 保留实际生产日志级别；不得一轮关闭访问日志、另一轮开启。指标按 5 秒抓取，阶段边界保存快照；不在请求循环中打印逐请求日志 |
| 健康检查 | 四个 JAR 和所需依赖真实 health=UP，运行有限创建→GET→HEAD 冒烟，确认正确 Location、鉴权与 Kafka 投递 |

原 E2E 使用 Java `Xmx384m / ActiveProcessorCount=2`，MySQL buffer pool 256 MiB / max connections 100、Redis 128 MiB / noeviction、Kafka 堆上限 512 MiB。这些是小型功能夹具。压测必须另存显式资源清单：可以先测原值作为小配置基线，再建立另一个资源档比较，不能静默扩容后混合报告。

连接池以实际 bean 和运行指标为准：Command 手建业务 Hikari 池上限为 16，ID 专用池为 2，Redirect 的自动配置池为 8；不能把 production.properties 中通用 Hikari=8 当成全部模块的有效池大小。

压测监督脚本单独放在 `scripts/performance/`，保留原 E2E 的 20 分钟生命周期和测试语义。每次性能运行都有最大时长、目标地址白名单、数据增量和磁盘预算。实际执行时才启动环境，本次计划编写不启动服务。

## 3. 工具与计量规则

主工具采用 k6，版本在执行前固定并保存校验信息。采用 `constant-arrival-rate` 按档位施加请求，每次迭代只发送一个被测请求；注册、登录、取分组、生成请求数据、结果查账在测量区间之外。这样服务变慢时不会自动减少目标请求到达率，掩盖排队。参考 [k6 开放与封闭负载模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。

必须分别记录计划请求数、实际发出数、完成数、正确业务响应数、失败数和未发出的 `dropped_iterations`。后者可能来自 VU 配置不足或服务变慢，不能一律算作服务错误，也不能从报告中删掉；确认客户端充足后才判定服务容量。参考 [k6 dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)。

- GET / HEAD 一律 `redirects: 0`，只测收到短链接服务的响应，不跟随 Location 访问第三方。成功跳转必须同时满足 302 和预期 Location；HEAD 还要求空响应体。
- 为正常、未知短码、权限拒绝、限流检查分别设置预期 HTTP 状态。不能把 302 当成失败，也不能把正常跳转中的 429、503 当成成功。创建还要检查 JSON `code=0` 与响应字段，不能只看 HTTP 200。参考 [k6 响应判定](https://grafana.com/docs/k6/latest/javascript-api/k6-http/set-response-callback/)。
- 同时记录 HTTP duration、连接 / TLS 建连耗时和客户端完整调用耗时；报告 p50 / p95 / p99，样本足够时附 p99.9。默认使用 HTTP/1.1 keep-alive；新建连接 / TLS 握手压力另起场景。
- 负载请求不自动重试。幂等重试是独立业务场景；只读查账、初始化重试单独记录。
- 固定随机种子、短码集合、访问分布、URL / UA / Referer 大小和 Cookie 模式。普通基线使用固定长度、受控的重复访客 Cookie；新访客无 Cookie 单列，避免客户端 Cookie 行为让两轮用户分布不同。参考 [k6 Cookie 管理](https://grafana.com/docs/k6/latest/using-k6/cookies/)。
- 指标标签只使用固定接口名、场景、阶段、状态和配置 ID；不按原始 URL、shortUri、requestId、IP 建时间序列。用受限的去敏失败样本定位错误。

## 4. 数据与鉴权准备

先通过真实业务流程注册 20 个测试账号并等默认分组 READY，取得账号的真实 tenantId / username / authVersion。内部测试凭据由监督进程生成并从私有环境注入，不写入脚本、命令行展示或结果报告。

Admin 直连请求带 `X-Internal-Token`、`x-shortlink-tenant-id`、`x-shortlink-username`、`x-shortlink-auth-version`；沿用 Admin 和 Command 的实际主体校验。公开会话头 `username/token` 属于 Gateway 入口契约，不能误用于 Admin 直连而一直测到 401。

Redirect 直连使用专用可信来源：优先复用 E2E 已验证的 APISIX 网络命名空间，从该真实源 IP 访问宿主 `8003`，APISIX 本身不转发这一轮请求。Host 使用已配置短链域名；不靠伪造 X-Forwarded-For 绕过真实 peer 校验，不关闭安全过滤器。正式独立压测机如需专用 `/32`，只进入隔离配置并在记录中显式列出。

直连请求携带固定的 X-Forwarded-Proto 和受控 X-Forwarded-For；A/B 对照保持解析后的访客 IP 分布一致。它只用于已有可信调用链传递测试身份，不能用来伪造多个 APISIX 限流 key。

数据集从 1 万条真实创建的有效短链起步，再按磁盘 / 配额预算扩到 10 万；新链生成不在跳转测量期间进行。各配置对照使用相同逻辑数据、固定 seed 和相同访问序列，更新类用例使用独立集合。第一轮每个配置档的新增记录上限暂定 20 万，达到上限停止新增负载并记录“数据预算结束”，不把它算作容量失败。

写入确认轮必须在启动前计算 `预装量 + Σ(批次率 × 每批行数 × 全部预热/测量时长) + 余量`，并核对每租户默认 100 万行额度与磁盘预算；回收不会释放额度。若 20 万默认上限不足以覆盖三次确认，应先冻结一个足够的独立数据预算或降低本轮目标档，不允许中途删数据、调额度或缩短确认轮后仍宣称原档位通过。

创建负载的 `requestId` 使用 runId + 场景 + 账号 + 全局迭代序号，正常创建每次唯一；幂等场景固定请求体和 requestId。跨压测进程也必须唯一。记录租户额度剩余量，单账号与多账号创建分开测，避免租户额度行锁掩盖系统并行能力。配置中租户额度、账号数和请求体大小不随档位偷偷改变。

requestId 总长不超过当前契约的 96 字符。20 账号是多租户对照起点；必要时准备多个分组，但不能依靠无限增加租户规避单租户负载结果。

目标地址使用可控的测试内容源，固定响应大小和延迟，保留真实元数据 worker、Outbox 和 Kafka。没有可控内容源时，先使用明确标记的元数据固定失败路径作诊断，正常元数据成功路径列为未验收；不能持续抓取 example.com 等第三方，也不能放宽 SSRF 校验让私网目标冒充正常生产路径。元数据积压属于创建链路必须观测的成本。

| A3 | 同步批量创建 | `POST /api/short-link/admin/v1/create/batch`；每批 10 / 100 / 500 行，使用 originUrls / describes 等批量 DTO，独立档位 | 同时报告批次/s、成功行/s、ID/s、区间 / SQL 批次；501 行进入异步任务，不放入这组同步成绩 |

| A5 | 小工作集持续热跳转 | `GET /{shortUri}`；1 条、10 条、100 条分别测 | 302 正确有效吞吐、CPU / GC、周期性权威刷新、真实事件生产 |

正常创建使用 `domain/originUrl/gid/createdType/validDateType/describe/requestId`；过期时间按接口 GMT+8 格式生成。A4 保留 `fullShortUrl/originGid/gid/expectedVersion` 等真实字段，不能用旧版本反复请求把 409 吞吐写成更新容量。

发号器作为 A1/A3 的专项观测，不另造 HTTP 发号端点：当前 `nextId`、`reserveRanges` 是嵌入式库方法，真实单条及同步批量创建均使用区间预留。至少让每个被测 Command 实例在边界观察轮实际消耗约三个默认 10000 step 的号段，记录约 80% 消耗时预取、切段、500 行批量跨段、等待 / 失败、数据库领取次数、issued / discarded 和编码 CPU；不重置 ID 高水位制造边界。预留高水位增量不能当成功创建量。动态步长默认关闭，另轮测量且覆盖其反馈 / 冷却周期，不能用短测签收。若服务定位需要，再对库做独立微基准；微基准不能代替完整创建吞吐，也不依据历史 Leaf 宣传值签收。

创建接口有瓶颈时，可增加同请求体直连 Command `POST /api/short-link/v1/create` 的诊断对照。该结果单独标记，不能替代 Admin → Command 的 A1 结果。列表分页可能依赖 Analytics，不作为本轮未经核对的轻量读接口。

### 冷热定义必须符合当前实现

当前 `authority-ttl-millis=1000`，Route L1、Redis 路由值和本地 Policy 快照都受权威有效期约束；TTL 不允许通过配置延长到 1 秒以上。Route 和 Policy 回源共用 `cluster-origin-rate=200/s`，Route JDBC 回源并发默认 16，两个 resolver 的在途合并集合各有上界。

因此“预热一次”不表示整轮都命中缓存，“能容纳 10 万条缓存”也不表示能持续保持 10 万条权威快照有效。A5/A6 必须一起记录活跃工作集、复用周期和 503 原因，识别周期刷新造成的瓶颈。小热集高 QPS 与大工作集低回源预算是不同测量结果。

冷启动单列：固定集合，在专用新 Redis 命名空间 / 空 DB 和新 Redirect 实例下从低档位开始，记录前 30–60 秒，再记录稳定段；只重启 Redirect 属于“L1 冷、Redis 可能暖”，必须正确命名。不在运行中执行 FLUSHALL 或清理世代标记来制造假冷缓存。

## 6. 阶段 B：再从网关压测跳转

沿用 A5–A7 的数据、方法、Cookie、seed、资源与档位，唯一主差异是 URL 改为 APISIX 入口并设置正确 Host。原值基线先跑，随后才能进行单独的容量探索。

| 顺序 | 场景 | 配置与结果口径 |
| --- | --- | --- |
| B1 | 原保护配置下的热跳转 | 单来源 IP，依次 100 / 300 / 600 / 900 请求/s；测有效 302、时延和 Kafka，无业务容量结论时不强行跑满所有档 |
| B2 | 原保护配置的超额与恢复 | 先有 B1 的 900/s 稳定证据，再以单来源 IP 做 1100 / 1500 请求/s 短时输入；单列 429 和延迟，再降载恢复。若 B1 已触及服务瓶颈，暂不执行这组高档保护轮；不能把 429 吞吐加进成功跳转容量 |
| B3 | 网关容量探索 | 仅隔离 APISIX 路由副本显式设置与目标档位匹配的有限 rate / burst / conn；与原值结果分开。保留边界插件、日志、事件采集和 Redirect 内部预算 |
| B4 | 分布与冷路径对照 | 对 A6/A7 的相同集合、访问次序测端到端额外开销和错误来源；按方法 / 分布 / 状态分别报告 |
| B5 | 稳态与恢复 | 在通过档位保持 30 分钟；完成后降低负载并等待异步任务排空，确认内存、连接和队列恢复 |

B1–B5 完成后增加一轮受控共存检查：经 APISIX 的 GET 取 B 已通过档的约 70%，叠加 Admin 直连创建取 A 已通过档的约 10%，并以低频更新 / 回收观察传播。新写入使用独立集合，固定热点用于持续跳转；分接口报告变化及 Kafka / Command / MySQL 争用，不用混合总 QPS 替代单项结果。这轮仍不经过 Agent，也不启动统计查询负载。

生产原值：跳转 `limit-req rate=1000, burst=200`；管理 `rate=100, burst=100`；两路 `limit-conn conn=200, burst=100`。以真实 `remote_addr` 限制，节点内 worker 共享；不能将两个 worker 当作双倍额度。当前镜像的 limiter key 还拼接配置类型及版本；standalone 同文件路由版本相同，管理与跳转可能共用 key，尚不能声称两路完全隔离。原值基线保持仅一条路由施压，混合创建直连 Admin；路由前缀隔离修复另行验证。发送更多虚构 X-Forwarded-For 不会变成更多真实来源；多机若经同一 NAT 也可能共用一份额度。多来源测试必须记录实际源地址及流量分配。

本轮执行前冻结 `local-diag-poll50`：Java 每进程 Xmx384MiB / ActiveProcessorCount=2，Java cpuset 0–7、APISIX 4–7（2 workers）、依赖 8–11、k6 12–15；APISIX 与 Java 存在 CPU 交集，属于本机诊断。元数据明确走 `.local` 拒绝路径，poll=50ms（默认1000ms），不代表正常网页抓取。新增数据预算先冻结为50万行：批量仅探索，写入长时确认限A1的20账号场景；不声称所有写入场景均完成容量确认。按预装期间500条任务约40–53秒排空的观测，持久任务pending达到2000即停止新输入，保留5分钟恢复窗口；该门槛是本次诊断停止条件，不修改服务的生产限额。详见运行目录 `run-manifest.json`。

B3 优先真实多来源；若本机仅一个来源，只能调整专用隔离路由的有限阈值，提前保存配置摘要。每个资源 / 保护配置形成独立实验 ID；原值恢复后同时校验文件内容和实际允许 / 拒绝 / 恢复行为。不能通过关闭鉴权、延长权威 TTL、关闭风控或丢弃事件采集“优化”结果。

第一轮沿用 standalone / HTTP，与 A 比较数据面开销。正式 etcd 模式与 HTTPS 在正式环境参数确定后重测；HTTP 的容量不能当作 TLS 或正式集群容量。原 E2E 中的 2/s 和 conn=2 只验证机制，不复用为性能参数。

## 7. 档位、时长和收敛顺序

以下是首轮负载输入，不是性能承诺；遇到停止条件即停止上探。

| 对象 | 初始阶梯 |
| --- | --- |
| 单条创建 | 1 → 5 → 10 → 25 → 50 → 100 请求/s；仍稳定才按 1.5 倍上探 |
| 幂等 / 更新 / 回收 | 1 → 5 → 10 → 25 → 50 请求/s，与真实创建独立统计 |
| 批量 | 每个批量大小从 0.1 → 0.5 → 1 批次/s；再按预算上探，记录折算行/s |
| Redirect 热链直连、B3 | 100 → 300 → 600 → 1000 → 2000 请求/s；稳定才按 1.5 倍上探 |
| 大工作集 / 冷启动 / 未知短码 | 10 → 25 → 50 → 100 请求/s 起步；先识别共享回源预算，不照搬热链高档 |

先用 1 请求/s、30 秒校验脚本及事件；探索阶段每档 30 秒过渡 / 预热 + 90 秒测量，档间留恢复窗口，异步积压未恢复不进入下一档。发生拐点后在最后通过与首次失败之间缩小步长，最多追加 3 个探测点。

低频批次用整数 rate 与 timeUnit 表达，例如 1 次/10 秒表示 0.1 批次/s，不向 k6 传入不支持的小数 rate。探索阶段低频样本只用于找区间，按后续确认轮规则判断尾延迟。

探索只定位区间。候选容量点需要 2 分钟预热 + 10 分钟测量、独立重复 3 次，记录全部结果和波动；低频接口样本不足 1000 时延长有限测量或明确标记样本不足，不能硬算稳定尾延迟。每阶段先确认核心场景，再扩分布，避免一次同时跑满所有接口导致无法定位瓶颈。

A 完成后先形成接口容量与瓶颈表，再进入 B。同配置下对照相同实际发出率及相同成功响应条件的 A/B p99 和 CPU / 事件成本，不能拿不同负载点作简单相减。配对轮固定发生器机器、cpuset / 资源配额、网络命名空间、连接复用模式和归一化访客身份，记录 socket peer、入口到上游的实际路径及其网络差异。若直连与经网关的路由不可等价，结果只能称为“接入路径整体差异”，不能把全部差值归因于纯 APISIX 处理开销。

## 8. 预先固定判断标准

以下是首轮诊断预算，用于统一比较，**不是已经承诺的生产 SLA**。执行开始前写入 run-manifest；若后续调整，生成新的实验版本，不能回改失败轮的通过口径。

| 项目 | 正常稳态候选通过条件 |
| --- | --- |
| 业务正确性 | 错目标、跨租户泄漏、重复提交多次落库、短码冲突、HEAD 生成点击：0 次；发现即停止 |
| 有效请求成功率 | 对合法正常负载，预期正确响应比例 ≥99.9%；业务拒绝 / 未知短码场景单独判定，不稀释此指标 |
| 延迟 | Admin 单条创建 / 更新 p99 ≤500 ms；合法稳态 GET 各分布分别要求 Redirect 直连 p99 ≤50 ms、APISIX p99 ≤80 ms；同步批量按 10/100/500 行先设 p99 ≤1/3/5 秒并单列。冷启动瞬态另报，不冒充稳态通过 |
| 发生器 | 测量段 dropped_iterations=0，实际发出达到计划的 99% 以上；压测端没有 CPU / 文件描述符 / 端口瓶颈 |
| 正常事件采集 | Redirect click/result 及 APISIX EDGE rejected/failed 增量均为 0，缓冲不持续增长，结束后有界排空；HTTP 达标但丢事件不计为可靠容量 |
| 持久任务 | Outbox 与元数据未出现持续增长的未处理量和最老任务年龄；结束后在预设 drain 窗口内恢复。Outbox 死信 / 终态失败为 0；元数据成功路径要求完成且无意外失败，固定失败路径按预设原因单列，不得因任务全失败后队列为空而判正常 |
| 稳态 | 无 OOM / 进程重启、连接泄漏或持续内存增长；30 分钟稳定观察可复现候选档位 |

探索中的 429 / 503 可以证明保护生效，但该档位不算正常可靠容量。B2 故意超额时不套“正常错误率”判失败，要检查有限拒绝及降载后的恢复；同时保留全部拒绝数量。

停止上探并降载：连续 30 秒意外错误率 >1%，或连续 3 个观测窗口超过延迟预算；出现事件采集丢失、Outbox / 元数据连续 3 分钟正向增长、事件队列持续 30 秒超过字节预算 80%，同样停止上探。OOM、错误目标 / 权限问题、依赖不可写立即停止。磁盘剩余低于 15% 或 10 GiB、压测端持续饱和时终止该轮，保存原因。

降载后观察最多 5 分钟：停止新创建 / 更新输入，跳转降至 `min(300/s, 最后通过档位的30%)`，连续 6 个 5 秒观测窗口内错误率 / p99 回到本轮预算、Hikari 等待连接数为 0、在途请求和内存回到稳定基线；随后停止业务输入，要求 Redirect 与 APISIX 各事件队列 pending=0、持久任务排空且没有意外终态失败。允许保留的初始化背景任务单独标识，不计为负载积压。

未恢复则本轮失败并保留证据；恢复后也不把先前失败点改成通过。首轮“可靠容量”取满足对应场景预算并完成复测的最高有效业务吞吐；可建议后续入口暂按其 70% 留运行余量，但单机余量不能替代 N-1 验证。

## 9. 观测必须落到已有能力与缺项

| 层级 | 当前可用 | 压测前需要补充 / 校核 |
| --- | --- | --- |
| 客户端 | 已实现并执行k6 2.2.0固定到达率脚本 | 已记录分阶段检查、实际发出 / 完成 / 正确 / dropped及端到端耗时；本轮HTTP无TLS，不能给出TLS成本 |
| JVM / HTTP | Actuator Prometheus：JVM 内存、CPU、HTTP 计数；Redirect Hikari active/pending/timeout | 现模板只抓 Gateway/Redirect，应把 Admin/Command 的本机管理端口 8102/8101 纳入；核对分位直方图是否实际开启 |
| Redirect 事件 | `shortlink_events_{delivered,rejected,failed}_total`、`shortlink_events_pending_bytes`，click/result 两 lane；内部 quality 有 attempted/delivered/failed/rejected/pending | 使用本次 producerInstanceId 和测量段增量，捕获 Kafka ACK / 交付稳定性 |
| APISIX 边缘事件 | 容器本机9099 `/shortlink/metrics` 已补attempted、pending count/bytes、worker启动世代及观测完整性 | 本轮12项真实接线校验通过；pending包含发送中的事件。每路由实时延迟、活动请求等仍未形成完整指标，不能假定已有完整APISIX Prometheus插件 |
| ID | current.remaining、next.ready、requested.step、refill.failures、executor.rejections、discarded、issued 等 7 项 gauge | DB 领取次数 / 区间数目前未全部导出；用数据库语句增量或新增低基数计量。不能仅看 issued 推算 DB 调用次数 |
| 缓存 / 回源 | 可读配置和受限路径，有实际 DB / Redis 调用 | 当前没有完整 L1/L2/policy 命中指标；需要接入命中、回源原因和 in-flight 计量，或用明确限制的数据库 / 调用采样；未采集项标 N/A，不能估算成实测 |
| 依赖 | 真实 MySQL / Redis / Kafka | 每阶段采集锁等待 / 连接 / 查询量，Redis 内存 / evictions / 命令延迟，Kafka 字节 / 分区偏斜 / 磁盘 / 生产端延迟，Outbox / 元数据队列长度及最老年龄 |

正常轮保留 Kafka 两条原始流及 APISIX 边缘采集。直连成功 GET 通常有一条 click 和一条 REDIRECT result；经网关还可能增加 EDGE result。按实际契约、原始 bytes 和状态计量，不能假定每次跳转只有一条 Kafka 消息。

`shortlink_events_rejected_total` 和 APISIX `shortlink_edge_events_rejected` 表示事件入队拒绝；它们与 HTTP 429 是两种损失口径，必须分图展示。容量判定不能用其中一个替代另一个。

本轮不启动完整统计消费者，所以不能用“无业务 consumer lag”证明统计跟得上。保留 Kafka 持久日志，按测量窗口边界 offset + 生产者计数核对；如额外起只读校验消费者，标明它不是 Flink / ClickHouse。高压下不全量导出访客原始消息，以汇总计数和有限去敏样本为主。

在低负载与拐点各采一次有界 JFR / CPU 采样，区分 Feistel/Base62 编码、账号校验、序列化、缓存键哈希、Redis / JDBC 等成本。详细采样轮单列开销，避免让诊断采样改变最终确认容量。
