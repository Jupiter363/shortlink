# 接入调度与发送组织优化执行报告

日期：2026-09-09。依据[分阶段执行计划](../../plan/生产级重构增强/23-网关瓶颈分阶段执行计划.md)，在 `codex/production-refactor-v07` 分支执行。接入调度修复、发送组织调整、编码热点评估和三轮持续组件验收均已完成；扩CPU可用范围的对照未带来收益。短窗口峰值与持续容量分开报告。

**范围纠正：本报告的8k通过与20k失败全部来自固定302上游的网关组件实验，没有执行真实Redirect或Redis短链查询。这些结果用于定位网关问题，不能回答真实跳转业务QPS。从网关进入真实跳转的压测已另行完成，业务结果见[真实网关跳转压测](25-真实网关跳转压测与验收.md)。**

## 已确认的原因

原来的低吞吐不是整台机器或 Kafka broker 的统一硬上限，至少有以下可以区分的成本：

1. **单 worker 的持续处理与接入公平性。** 6,000/s 冷接入时，单 worker 后两秒 on-CPU 99.888%；正式三秒253次epoll返回只接入253条HTTP连接。能够关联的请求中，写完到accept的等待下界P99达到2592.44ms。线程一直在做工作，不能归因为始终得不到CPU调度。
2. **网关初始FD表扩容。** 四worker基线中，每个worker在accept返回FD64、128时均出现20.810–59.219ms的D等待。启动时预分配到至少1024后，512次HTTP accept内的D等待合计由248.995 worker-ms降为0，最大accept耗时0.108ms。D合计是跨worker累计，不能解释为宿主墙钟。两个实验均为无丢失的accept-only内核取证，不包含read时间。
3. **发生器自己的冷启动停顿。** 新发生器相同二进制、相同服务端配置，仅切换FD准备选项，关闭时在fresh累计62、126、253附近出现30.87、8.00、28.57ms的全记录进展空档；开启后首200ms没有≥2ms的同类空档。准备在测量前完成，无业务预热，512条HTTP连接仍是首次连接。
4. **发送过碎导致RPC和编码放大。** 发送槽增多不等于CPU并行度提高。在固定节点队列预算下，更充分地攒批显著减少Produce调用，Kafka CPU随之下降，说明此前不能单凭跳转与统计积压就认定broker容量不足。

Linux v6.6的FD表扩容路径包含共享文件表条件下的RCU等待，和当前FD边界、D状态及预分配对照相符；本轮没有采到对应内核栈，不将具体RCU栈当成已直接测得的事实。[Linux v6.6源代码](https://raw.githubusercontent.com/torvalds/linux/v6.6/fs/file.c)

## 修正与被否决的方案

- **不采用单独开启multi_accept。** 它让新连接更快被accept，但接受后首次read P99达到121.82ms；12,416个正确HTTP只有6,996条ACK/Kafka，另外5,420条队列拒绝。接入改善同时交付退化，不能算整体优化通过。
- **发生器修正单独归因。** 网关配置相同的关闭/开启对照中，正确HTTP=ACK=Kafka从17,976变为18,000；24次未发包括23次SOURCE_BUSY和1次末尾超窗。HTTP P99为43.211→3.050ms，scheduled-to-completion P99为80.835→3.382ms。这个改善属于测量工具修正，不计为网关产品收益。
- **网关FD准备是初始容量准备。** 它不修改nofile，不增加worker_connections，也不能消除超过1024编号空间后的后续扩容。产品接线须保护模块加载/初始化失败，保留原统计注册，并使失败可见。

## 编码、持续容量与最终验收

七段无 yield 的线程 CPU 采样已完成。采用 1/128 采样，在相同 4 worker、6,000/s、30 秒预热加 5 秒测量中，开启与关闭采样两组均为 121,500 个正确 HTTP=ACK=Kafka，无未发、拒绝或失败。正式窗估计占网关 CPU 的比例为：账本构造 1.243%、账本 JSON 8.147%、事件 JSON 3.075%、Kafka message-set 2.760%；扣除空采样钩子中位数后的估计分别为 0.873%、7.777%、2.787%、2.701%。这些是采样估计，不是逐次完整计时。

本轮不修改编码实现。账本构造采样还包含最老项扫描及嵌套 HTTP snapshot，外层表分配只是其中一部分；预计收益不足以支持改动原子发布、世代和排空语义。账本 JSON 是这些编码项中最大的一项，但当前证据不足以把它认定为尾延迟根因，也不支持立即引入新的状态发布协议。保留后续优化入口，不凭热点排名直接重写。

## 8,000/s 的三轮持续验收

三轮使用同一产品、发生器二进制与1024个owner、4 worker/每worker 1 sender/5ms、节点1000条/8MiB、网关2物理核/4逻辑CPU、HTTP桩及真实Kafka。每轮30秒预热加60秒正式窗口，三轮正式计划cohort共1,440,000次，全部正确完成；含预热共1,804,500 HTTP=ACK=Kafka，零未发、HTTP错误、事件拒绝或交付失败。

| 轮次 | 严格窗口完成QPS | HTTP P99 | 计划到完成P99 | HTTP最大值 | 网关平均CPU | pending采样峰 / 最老年龄峰 |
|---|---:|---:|---:|---:|---:|---:|
| r1 | 7,999.9500 | 24.784ms | 25.227ms | 107.418ms | 219.732% | 98条 / 26ms |
| r2 | 8,000.0000 | 1.637ms | 1.769ms | 17.560ms | 200.372% | 52条 / 7ms |
| r3 | 8,000.0167 | 21.294ms | 22.138ms | 177.483ms | 235.086% | 97条 / 47ms |

正式窗口按实际完成时刻共计1,439,998次，和按计划归属的1,440,000次差别来自跨窗完成；尾部完成没有提前算入QPS。三轮均通过原双P99≤80ms门槛，但仍有167个正式请求超过80ms，不能解释为最大延迟也小于80ms，更不能只报表现最好的第二轮。

三轮完全落在正式窗内的指标采样，ACK加权速率分别为7,999.72、8,000.00、8,000.19/s。队列首末分别37→49、30→30、36→28。第一轮首末五秒pending均值24→55且末十秒有较高波动，峰98后回落至49；第三轮峰97后回落至28。结合全部区间交付、回落、零拒绝和最终排空，**本轮60秒×3范围内未观察到持续累积，8,000/s组件稳定档通过**。这不是多小时运行的漂移证明，采样峰值也不是连续时间最大值。

自动核查见 `.work/gateway-execution-20260909/stable-platform-audit-final.json`，其工具合同只判断一致性，容量标志保持false；根节点的独立人工趋势复核及明确范围结论保存在 `stable-component-review.json`，没有改写原结果。持续实验runner原字节已归档为 `run-stable-frozen.py`，随后CPU对照工具变动不会覆盖原验收证据。

上述通过只适用于该4 worker组件profile。2 worker只在节点1000条/8MiB组件预算下完成6,000/s短验收，也不是仓库默认2000条/16MiB的完整profile。不能将4 worker长测结果直接套到默认部署，也不能套到带TLS、生产限流器和真实Redirect/消费者的完整业务链路。

**扩大CPU可用集合没有解决问题。** 两组网关使用量仍约4个逻辑CPU单位；扩大eligible CPU集合并不增加4个worker的执行线程数。扩范围组部分统计拒绝更少，同时HTTP到达也更少，不能把拒绝数下降解释为优化通过。这里的核心映射来自guest内核，不是宿主物理核心独占证明；没有采集逐次run-on-CPU事件，不能声称worker实际使用了新增8–9。

高负载下的判断是：当前瓶颈集中在**网关4个worker的执行能力与事件投递推进**，而不是已被证明的整机硬件上限。原20k坏区间网关CPU约398%，发送槽wall占比93–96%，交付降到约14.65k–17.63k/s；中间区间约376–386% CPU时交付可回到约20k/s。发送耗时含CPU、yield和事件循环等待，不能全部算成broker ACK耗时。worker请求分配均衡，原20k各worker占比24.76%–25.24%；worker本地队列满时，节点总队列未必已经满1000。

**目前没有依据优先扩Kafka broker，也不能建议仅加宽cpuset就能提高容量。** 更高容量的下一项验证应是有效worker并行度及高负载下的sender组织，并保持节点预算不变；同时使用能明确核验CPU执行位置的独立压力环境。4 worker和sender=1在接近满载时各自的因果贡献，仍需该单变量验证才能分开。桩CPU也已接近单worker的处理边界，完整业务容量必须恢复真实Redirect链路另测。当前没有证据要求立即重写统计架构。

本轮到此结束压测：已验证的持续下界是上述8k组件profile；16k是统计完整但有末端关窗未发送的短观察，20k多组真实交付失败。没有给出伪精确的“硬件最大QPS”。

## 证据范围和保留规则

本轮压力路径是APISIX→固定302桩，同时真实写入私有Kafka（单broker、两分区、复制因子1）。实验保留 shortlink-boundary 和逐请求事件 logger，但没有生产 limit-req/limit-conn 或 TLS。没有运行真实Redirect业务、统计消费者或Agent；结果是网关组件证据，不能用来宣称完整入口或业务容量。CPU拓扑为5800H的8物理核/16线程：网关0–3（2物理核、4逻辑CPU）、桩4–5、观察6–7、Kafka8–11、发生器12–15；整个WSL仍与Windows宿主共享硬件。

原失败不覆盖：网络初始化的两次失败有独立SHA绑定的零业务/零Kafka核账；一次编码关闭组的CPU采样最大间隙1.008秒发生在正式窗结束后约3.9秒，原观察门禁失败保留。正式窗内最大采样间隙101.45ms，只能按明确范围使用该部分CPU数据。后续runner将大JSON解析移到定时采样停止之后，避免解析阶段污染采样边界。

详细原始证据位于 `.work/gateway-execution-20260909/`，含每轮source SHA、实际容器身份、CPU约束、客户端逐请求、服务端关联、Kafka前后offset、初始化证明、失败记录和分析结果。历史数据未删除，也未通过重置Kafka计数刷新预算。
