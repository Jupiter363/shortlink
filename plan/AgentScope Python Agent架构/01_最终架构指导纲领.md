# Shortlink AgentScope Python Agent 最终架构指导纲领

> 状态：Approved Architecture Baseline  
> 版本：1.0  
> 日期：2026-07-17  
> 架构目标：完全下线 Java agent-service，以 AgentScope 2.0 为 Python Agent Runtime，同时保留 Java 业务系统的权威事实与确定性控制边界  
> 目标读者：架构师、技术负责人、Java/Python 工程师、SRE、安全工程师、测试负责人和产品负责人

## 0. 规范性语言

本文使用以下规范词：

- 必须：架构不变量，违反即不得上线。
- 不得：明确禁止的设计。
- 应：默认方案，偏离时必须提交 ADR 并说明收益、成本和回滚方式。
- 可以：允许的实现选择，不构成强制。

本文不是概念方案。它是后续详细设计、代码结构、接口定义、部署、安全评审和验收的上位约束。

## 1. 执行摘要

最终系统采用三层责任模型：

1. Python 智能控制面：AgentScope、模型、会话、工具编排、派生风险分析、评估和运行观测。
2. 隔离执行面：按租户和会话创建的 Sandbox，只处理动态代码、临时文件和脱敏数据。
3. Java 权威兑现面：身份、资源权限、业务事实、审批动作、风险策略、事务、幂等、Outbox 和 Gateway 热路径。

核心原则：

> Python 负责认知与派生，Java 负责事实与兑现。

最终形态中：

- Java 不再实现 Prompt、模型调用、Agent Graph、Agent Memory 或 Agent Runtime。
- Python 不直接修改短链业务事实，不直接发布 Gateway 风控策略。
- LLM 和 Sandbox 均不持有业务数据库凭据、内部服务主密钥或风险 Redis 写权限。
- 即使 Python、LLM、Sandbox 全部不可用，短链核心业务与 Gateway 已生效策略仍必须正确工作。

这不是语言替换，而是按一致性和风险重新划分系统边界。

## 2. 目标与非目标

### 2.1 目标

架构必须实现：

1. 完全下线现有 Java agent-service 模块及其 Spring AI Alibaba 依赖。
2. 使用 AgentScope 2.0 构建 Python Agent Runtime。
3. 支持租户、用户、会话三级隔离。
4. 支持生产级 Sandbox，隔离动态代码和租户文件。
5. 保持短链、统计、分组和权限事实由 Java 业务系统拥有。
6. 保持写操作必须经过提案、确认、授权、幂等和审计。
7. 保持 Gateway 风控热路径只依赖 Redis，不依赖 Agent、LLM 或数据库。
8. 支持同步响应与流式事件，最终以异步 Run + SSE 为主。
9. 支持确定性风险工作流，不把风险评分和策略执行交给自由 Agent。
10. 支持端到端追踪、成本预算、质量评估、灰度、回滚和灾难恢复。

### 2.2 非目标

第一阶段明确不做：

1. 不把 admin、project、gateway 主体改写为 Python。
2. 不让 AgentScope Permission 取代业务授权或审批状态机。
3. 不让 Sandbox 访问业务内网、MySQL、风险 Redis 或模型主密钥。
4. 不默认启用 Agent Team、多 Agent 自主协作、长期记忆或开放式 MCP。
5. 不引入分布式事务。
6. 不为了架构图完整而提前拆出大量微服务。
7. 不允许 LLM 直接生成并执行删除、禁用、封禁或策略写入。
8. 不以牺牲现有风险一致性和回滚能力换取迁移速度。

## 3. 现状判断与重新划界原因

现有 agent-service 同时承担了五种不同性质的职责：

1. Agent 认知：Campaign Analysis、Security Risk 解释、模型调用。
2. 派生计算：风险画像、规则评分、异常检测。
3. 业务控制：PendingAction、授权、执行器。
4. 策略一致性：有效策略槽位、Outbox、Redis 发布。
5. 平台基础设施：Checkpoint、Scheduler、Worker、Console、内部 API。

仓库基线证据：

| 项目 | 当前规模/事实 |
|---|---|
| agent-service 主代码 | 约 210 个 Java 文件、18,503 行 |
| agent-service 测试 | 约 93 个 Java 测试文件、23,526 行 |
| 直接引用 Spring AI Alibaba | 11 个文件、约 2,356 行，约占主代码 13% |
| Agent 数据表 | schema 中包含 checkpoint、pending action、批次、任务、风险、策略和 outbox 等 13 张核心表 |

关键实现参考：

- [agent-service/pom.xml](../../agent-service/pom.xml) 声明 Spring AI Alibaba 依赖。
- [DefaultCampaignAnalysisGraphExecutor.java](../../agent-service/src/main/java/com/nageoffer/shortlink/agent/campaignanalysisagent/graph/DefaultCampaignAnalysisGraphExecutor.java) 同时承载 Graph、Tool 规划、LLM 和响应组装。
- [DefaultSecurityRiskGraphExecutor.java](../../agent-service/src/main/java/com/nageoffer/shortlink/agent/securityriskagent/graph/DefaultSecurityRiskGraphExecutor.java) 编排确定性风险节点。
- [AgentPendingActionService.java](../../agent-service/src/main/java/com/nageoffer/shortlink/agent/harness/action/service/AgentPendingActionService.java) 实际承担业务审批、CAS、租约和重放安全。
- [agent_service_schema.sql](../../agent-service/src/main/resources/sql/agent_service_schema.sql) 展示认知、派生和权威数据目前共库的现状。

这五类职责放在同一 Java 模块中可以运行，但不适合作为 Python 迁移边界。若整体平移：

- AgentScope 只能直接替代认知和部分平台能力。
- 事务、权限、Outbox 和 Gateway 契约仍需重新实现。
- Python 将同时成为概率性推理系统和权威策略写入系统，扩大事故半径。

因此最终架构按权威性拆分，而不是按原目录平移。

### 3.1 决策测试

任何新能力必须先通过以下判断：

| 问题 | 是 | 否 |
|---|---|---|
| 输出是否依赖 LLM、Prompt、向量检索或动态代码 | Python | 继续判断 |
| 输出是否可以从事实数据重新计算 | Python 派生域 | 继续判断 |
| 是否修改权威业务状态 | Java | 继续判断 |
| 是否要求数据库事务、幂等、审批或审计 | Java | 继续判断 |
| 是否位于跳转或风控热路径 | Java/Gateway | 继续判断 |
| 是否处理租户临时文件或不可信代码 | Sandbox | 普通应用服务 |

## 4. 架构不变量

以下规则是系统最高优先级约束。

### 4.1 权威性不变量

1. Java 是短链、分组、统计权限、审批动作和有效风险策略的权威系统。
2. Python 产生分析、建议、画像、解释和提案，不产生已执行的业务事实。
3. 任何业务写操作必须经过 Java Command API。
4. Gateway 只读取版本化风险 Redis，不调用 Python、LLM、MySQL 或 admin。
5. LLM 输出只能作为建议或受约束输入，不能成为策略写入凭据。

### 4.2 数据不变量

1. 每张表只有一个服务拥有写权限。
2. Java 和 Python 不共享表所有权。
3. Agent Session Redis 与 Gateway Risk Redis 必须使用不同 ACL；生产建议使用不同实例或集群。
4. Restricted 数据不得进入 Prompt、模型、Sandbox、普通日志或前端响应。
5. Tool 结果必须带来源、时间、范围和快照标识。

### 4.3 租户不变量

1. 所有运行态资源必须绑定 tenant_id、user_id、session_id。
2. tenant_id 不等同于 gid；gid 是租户内业务资源。
3. Python 不得信任请求体中的 username、tenantId 或 userId。
4. Java 必须对每次 Capability 和 Command 调用重新授权。
5. 相同 sessionId 在不同租户或用户下必须被视为不同资源，并禁止互读。

### 4.4 执行不变量

1. Sandbox 默认无业务网络、无业务凭据、无宿主目录挂载。
2. 自定义 Tool 不会因为使用 AgentScope 就自动进入 Sandbox，必须显式选择执行位置。
3. 对非幂等 Command 不得进行透明自动重试。
4. 所有异步事件按至少一次投递设计，消费者必须幂等。
5. 所有 Agent Run 必须有截止时间、模型预算、Tool 预算和 Sandbox 预算。

### 5.1 最终上下文图

### 5.2 为什么浏览器最终直接访问 Python Runtime

禁止把最终流量固定为：

~~~text
Browser -> admin -> Python -> admin
~~~

该同步调用环会造成：

- Java servlet 线程等待 Python，Python Tool 再占用新的 Java 线程。
- 流式连接长期占用 admin 资源。
- 熔断、超时和容量规划形成闭环。
- admin 成为模型流量的数据转发层。

最终方案使用 Session Bootstrap：

~~~text
Browser -> admin: 创建 Session Grant，获取短期 Runtime Token
Browser -> Gateway -> Python: 提交 Run 与订阅 SSE
Python -> Java admin: 调用 Capability 或提交 Action Proposal
Browser -> admin: 确认或拒绝 Action
~~~

admin 只创建权威的 Session Grant，不同步调用 Python。Python 在首个合法 Run 到达时懒创建 Runtime Session。Session Grant 描述“谁被允许使用哪个 session”，Runtime Session 描述“Agent 当前运行到哪里”，两者不得共表。

迁移阶段可以保留 admin 代理兼容接口，但不得作为最终架构。

## 6. 分层与组件职责

### 6.1 Experience Plane

组件：

- Admin Web
- Gateway
- Java Admin Session Bootstrap API

职责：

1. 完成用户登录和基础页面访问。
2. 创建 Agent Session。
3. 获取短期 Agent Delegation Token。
4. 通过 Gateway 访问 Python Run API。
5. 展示流式事件、卡片、数据来源和待确认动作。
6. 写操作确认始终调用 Java admin，不调用 Python 执行。

### 6.2 Java Authority Plane

第一阶段作为 admin 内部的严格模块化边界实现：

~~~text
admin
  authority/
    identity/
    capability/
    approval/
    riskcontrol/
    audit/
~~~

职责：

- Identity：认证用户，签发 Delegation Token。
- Capability：提供 Agent 可消费的只读、语义化业务能力。
- Approval：保存、确认、拒绝和执行待确认动作。
- RiskControl：验证风险评估，管理有效策略和 Outbox。
- Audit：记录权威命令和人工处置。

这不是 Java Agent Service。它不包含 Prompt、模型、Memory、Agent 编排或 Sandbox。

仅在满足以下任一条件时，才应从 admin 提取独立 Authority Service：

1. 独立团队负责且发布节奏持续冲突。
2. 权威命令 SLO 与 admin 差异显著。
3. 容量或安全隔离无法通过模块化和资源池解决。
4. 需要独立数据库生命周期或跨多个 BFF 复用。

没有触发条件时，不得为追求微服务数量提前拆分。

### 6.3 Java Project Plane

project 继续拥有：

- 短链创建、更新、分页和回收。
- 统计事实。
- URL title 等业务能力。

Agent 不得直接绕过 admin 访问 project。Java Authority Plane 负责用户资源授权和命令协调。

### 6.4 Gateway Enforcement Plane

Gateway 继续：

- 读取版本化风险 Redis。
- 在本地完成策略匹配和限流/拦截。
- 保留最后一次已成功加载的策略。
- 不同步调用任何 Agent 服务。

Python Agent Runtime 不在跳转热路径上。

### 6.5 Python Intelligence Control Plane

Python Agent Service 包含：

~~~text
API Facade
Identity Context
Agent Runtime Port
AgentScope Adapter
Tool Gateway
Prompt Registry
Model Gateway
Session Service
Run/Event Service
Risk Analysis Workflow
Worker Runtime
Sandbox Orchestrator
Evaluation Hooks
Observability
~~~

职责：

- 接收和管理 Agent Run。
- 运行 Campaign Agent。
- 运行确定性的 Risk Analysis Workflow。
- 管理短期会话、上下文压缩和流式事件。
- 调用 Java Capability API。
- 创建 Action Proposal。
- 管理 Sandbox 生命周期。
- 保存派生画像、评估、Trace 和数据来源。

### 6.6 Sandbox Execution Plane

Sandbox 是独立执行面，不是 Python API 进程中的子进程。

职责：

- 执行 Python/Pandas 等动态分析。
- 处理租户上传的临时文件。
- 生成图表和报告产物。
- 在受控配额内运行不可信代码。

Sandbox 不负责：

- 调用业务 Capability API。
- 访问 MySQL、Redis 或消息总线。
- 保存权威业务状态。
- 持有模型或内部服务凭据。

## 7. 身份与多租户

### 7.1 Tenant Context

统一上下文：

~~~json
{
  "tenantId": "tenant-default",
  "userId": "u-10001",
  "sessionId": "as-s-01...",
  "scopes": [
    "agent:run",
    "capability:stats:read",
    "action:proposal:create"
  ]
}
~~~

当前系统即使只有单逻辑租户，也必须使用 tenant-default 显式填充，不得省略 tenant_id。

### 7.2 Agent Delegation Token

admin 签发短期非对称 JWT：

| Claim | 含义 |
|---|---|
| iss | shortlink-admin |
| aud | shortlink-agent-runtime |
| sub | 权威 userId |
| tid | tenantId |
| sid | sessionId |
| scp | 最小权限 scopes |
| jti | 防重放标识 |
| iat/nbf/exp | 生命周期 |
| ctx_ver | 身份上下文版本 |

要求：

1. 应使用 ES256 或等价的非对称签名。
2. Python 通过 JWKS 验签并缓存公钥。
3. Token 默认有效期 5 分钟，可通过 admin 刷新。
4. 不得把 Token 放入 URL query。
5. Token 不得包含手机号、真实姓名或敏感业务数据。
6. Runtime Token 只能访问 Python，不得直接访问 Java Authority。

### 7.3 服务身份

用户身份与服务身份必须同时成立。Python 使用 mTLS/workload identity 将 Runtime Token 交换为更短时效的 Authority Token：

~~~text
Browser -> Python:
  Runtime Token，aud = shortlink-agent-runtime

Python -> Java:
  mTLS / workload identity
  + Authority Token，aud = shortlink-authority
  + act = shortlink-agent-runtime
~~~

Token Exchange 必须保证 Authority Token 的 scope 是 Runtime Token scope 的子集，过期时间不得超过原 Token，建议不超过 2 分钟。

迁移期可以兼容 X-Agent-Internal-Token，但最终必须移除静态共享密钥。

### 7.4 授权原则

- Python Permission 用于缩小模型可见工具范围。
- Java Authorization 用于最终资源授权。
- Python 可以预检查 gid，但 Java 必须再次验证 gid 所有权。
- Tool 输出不得包含调用者无权访问的数据，即使 Prompt 请求绕过权限。

## 8. Agent Runtime 设计

### 8.1 AgentScope 封装

业务代码不得直接依赖 AgentScope 的 HTTP DTO 或内部存储结构。

定义稳定端口：

~~~python
class AgentRuntimePort(Protocol):
    async def start_run(self, command: RunCommand) -> RunHandle: ...
    async def resume_run(self, command: ResumeCommand) -> RunHandle: ...
    async def cancel_run(self, command: CancelCommand) -> None: ...
~~~

AgentScope 通过 AgentScopeRuntimeAdapter 实现该端口。

目的：

- 固定 AgentScope 版本并隔离升级。
- 允许测试使用 Fake Runtime。
- 防止框架对象渗透到领域和 API。
- 允许未来替换模型或局部编排实现。

### 8.2 Campaign Agent

Campaign Agent 采用受约束 Agent Loop：

~~~text
Input Guard
-> Deterministic Slot Resolver
-> Bounded AgentScope Reason/Act Loop
-> Tool Result Normalizer
-> Deterministic Insight Calculator
-> Structured Response Composer
~~~

默认预算：

| 预算 | 默认上限 |
|---|---:|
| Run wall time | 60 秒 |
| Model calls | 4 |
| Tool calls | 8 |
| 并行只读 Tool | 4 |
| Sandbox executions | 2 |
| 单次 Tool 结果 | 1 MiB |
| 最终回答 | 2000 tokens |

预算必须按租户和 Agent 类型可配置，但服务端硬上限不可由 Prompt 修改。

### 8.3 Security Risk Workflow

Security Risk 不是自由 Agent，采用显式工作流：

~~~mermaid
flowchart LR
    A["Load Candidate Snapshot"] --> B["Fetch Features"]
    B --> C["Deterministic Rules"]
    C --> D["Risk Scoring"]
    D --> E["Optional LLM Explanation"]
    E --> F["Persist Assessment"]
    F --> G["Create Action Proposal"]
    G --> H["Compose Result"]
~~~

规则：

1. LLM 不参与 riskScore、reasonCode 和 autoEligible 计算。
2. LLM 失败时仍保存确定性评估。
3. 只有确定性规则结果可以触发自动候选动作。
4. Python 只能提交 RiskPolicyProposal，Java 决定是否激活。
5. rulesetVersion、featureSnapshotId 和 evidenceHash 必须进入评估。

### 8.4 Model Gateway

模型访问通过 ModelGatewayPort：

- 统一超时、重试、Token 统计和错误分类。
- 统一数据分类和 Provider 允许策略。
- 统一结构化输出校验。
- 统一熔断和成本预算。

模型切换属于可逆决策，领域代码不得依赖某个 Provider 的响应对象。

自动 fallback 只允许用于解释和只读分析；涉及数据驻留或租户模型策略时必须禁用跨 Provider fallback。

### 8.5 Prompt Registry

每个 Prompt 必须包含：

- promptName
- promptVersion
- agentType
- inputSchemaVersion
- outputSchemaVersion
- owner
- changeReason
- evaluationDataset

生产 Prompt 不得以散落字符串形式存在。Prompt 变更必须经过离线评估和灰度。

## 9. Tool 架构

### 9.1 Tool 分类

| 类型 | 执行位置 | 示例 | 风险 |
|---|---|---|---|
| QueryTool | Python 宿主 -> Java Capability | 分组、短链、统计 | 低 |
| DerivedTool | Python 宿主 | 排名、趋势、规则计算 | 低 |
| SandboxTool | Sandbox | Pandas、文件分析 | 中 |
| ProposalTool | Python 宿主 -> Java Approval | 创建短链提案、策略提案 | 中 |
| CommandTool | 不向模型暴露 | Java 确认后执行 | 高 |

模型永远看不到 CommandTool。

### 9.2 Tool Descriptor

每个 Tool 必须声明：

~~~json
{
  "name": "get_group_stats",
  "version": "1.0",
  "readOnly": true,
  "executionZone": "HOST",
  "requiredScopes": ["capability:stats:read"],
  "timeoutMs": 5000,
  "maxAttempts": 2,
  "idempotency": "SAFE",
  "inputSchema": "get-group-stats-input-v1",
  "outputSchema": "get-group-stats-output-v1",
  "dataClassification": "CONFIDENTIAL",
  "maxOutputBytes": 1048576
}
~~~

### 9.3 Tool 调用规则

1. 只读请求可以在超时和幂等约束下有限重试。
2. Command/Proposal 只在携带 idempotencyKey 时允许调用。
3. Tool 错误必须结构化，不得把堆栈注入 Prompt。
4. Tool 输出必须先脱敏、截断和 Schema 校验。
5. 外部内容一律标记为 untrusted data，不得提升为系统指令。
6. Tool Gateway 必须记录 toolCallId、snapshotId、latency、status 和 traceId。

### 9.4 数据快照

Tool 返回的数据来源：

~~~json
{
  "snapshotId": "snap-01...",
  "source": "java-capability/group-stats",
  "scope": {
~~~

## 10. Sandbox 架构

### 10.1 隔离粒度

默认一个 tenantId + userId + sessionId 对应一个临时 Workspace。

同一会话可以复用 Sandbox 以降低冷启动，但必须：

- 设置最大生命周期。
- 每次 Run 清理进程和临时句柄。
- 会话结束、Token 撤销或 TTL 到期后销毁。

不得跨用户复用可写 Workspace。

### 10.2 环境选择

| 环境 | 实现 |
|---|---|
| 本地开发 | Local Workspace |
| 集成测试 | Docker Sandbox |
| 生产 | OpenSandbox 或 Kubernetes Sandbox |

生产不得使用 Local Workspace 作为安全边界。

### 10.3 网络与凭据

生产 Sandbox 默认：

- deny-all egress。
- 禁止访问 RFC1918 内网、metadata endpoint 和宿主网络。
- 不注入数据库、Redis、模型或内部服务凭据。
- 不挂载 Docker Socket。
- 不挂载宿主工作区。
- 根文件系统只读，单独提供限额临时卷。

确需联网时必须通过 Egress Proxy 白名单并记录审计。

### 10.4 资源配额

必须限制：

- CPU
- memory
- ephemeral storage
- PID
- wall time
- stdout/stderr 大小
- 单文件大小
- 产物数量
- 并发 Sandbox 数

资源超限是业务可识别错误，不得无限重试。

### 10.5 数据交换

Sandbox 输入只能是：

- 已脱敏 Tool Snapshot。
- 用户明确上传且通过检测的文件。
- 由 Python 控制面生成的只读任务说明。

Sandbox 输出：

- 结构化 JSON。
- 受限文本。
- 产物文件清单及哈希。

输出必须经过恶意内容、敏感信息、Schema 和大小校验后才可进入 Agent 上下文。

### 10.6 产物存储

大文件不得写入 Redis 或 MySQL BLOB。

应使用对象存储：

- 本地/测试可使用 MinIO。
- AWS 可使用 S3。
- DB 只保存 artifactId、tenantId、owner、hash、mediaType、size、retention 和 objectKey。

Sandbox 不持有对象存储长期凭据，由控制面完成上传下载或签发严格受限的短期 URL。

## 11. 审批动作与权威命令

### 11.1 状态机

~~~mermaid
stateDiagram-v2
    [*] --> PENDING
    PENDING --> EXECUTING: confirm + version CAS
    PENDING --> REJECTED: reject
    PENDING --> EXPIRED: ttl reached
    EXECUTING --> EXECUTED: command committed
    EXECUTING --> FAILED: execution failed
    FAILED --> EXECUTING: replay-safe retry
    EXECUTED --> [*]
    REJECTED --> [*]
    EXPIRED --> [*]
~~~

### 11.2 Proposal 内容

Action Proposal 必须包含：

- actionId
- tenantId
- ownerUserId
- actionType
- targetType/targetKey
- canonical payload
- payloadHash
- evidence summary
- snapshot references
- idempotencyKey
- expected resource version
- expireTime
- sourceAgent/runId/traceId

### 11.3 执行原则

1. Python 只创建 Proposal，不执行业务命令。
2. 用户确认调用 Java admin。
3. Java 重新检查用户、租户、gid、动作类型和资源版本。
4. 通过 CAS 抢占执行权。
5. 执行结果和审计在权威事务中持久化。
6. 重复确认返回已执行结果，不重复执行。
7. 非 replay-safe 动作失败后不得自动重放。

AgentScope 的 ASK/ALLOW/DENY 只用于交互体验和模型工具约束，不取代该状态机。

## 12. 风险策略控制

### 12.1 风险评估与策略分离

Python 产生 RiskAssessment：

~~~text
事实快照 + 确定性规则 + 分数 + 证据 + 可选 LLM 解释
~~~

Java 产生 EffectiveRiskPolicy：

~~~text
授权 + 策略资格校验 + 人工确认/自动资格 + 版本 + Outbox
~~~

两者不得合并为一个模型输出对象。

### 12.2 自动动作

自动动作必须同时满足：

1. actionType 位于 Java 配置的 auto-eligible allowlist。
2. 评估包含受信任 rulesetVersion。
3. score 和 reasonCode 满足 Java 硬阈值。
4. assessmentId/idempotencyKey 未处理。
5. 目标仍属于当前租户且状态允许。
6. 评估未过期。

LLM recommendation 不参与自动资格判断。

### 12.3 Outbox 一致性

权威数据库事务中同时提交：

- risk policy history
- effective policy slot
- policy sync outbox
- action audit

Outbox Worker 异步发布 Redis。

Redis payload 必须携带 policyId 和 policyVersion。删除必须使用 compare-and-delete Lua，旧版本撤销不得删除新版本。

### 12.4 Gateway 降级

- Redis 暂时不可用时，Gateway 使用本地最后已知有效策略。
- 策略同步失败时 Outbox 重试，不回滚已提交的数据库事实。
- Python 不可用时，Gateway 已生效策略不受影响。
- 对每种策略明确 fail-open 或 fail-closed，禁止使用全局模糊开关。

## 15. 一致性与幂等

### 15.1 不使用分布式事务

跨语言状态变化使用：

~~~text
本地事务 + Outbox + 至少一次事件 + 幂等 Inbox
~~~

### 15.2 幂等键

建议格式：

~~~text
agent run:
  tenantId:userId:clientRequestId

action proposal:
  tenantId:actionType:targetKey:payloadHash

risk assessment:
  batchId:gid:targetKey:rulesetVersion

policy activation:
  assessmentId:actionType:policyConfigVersion
~~~

幂等键必须有唯一约束，不能只依赖 Redis 锁。

### 15.3 并发控制

- API Run：session 级互斥或明确允许队列化。
- Risk Job：数据库 lease + ownerToken + leaseUntil。
- Approval：version CAS + executionToken。
- Effective Policy：policyKey 唯一槽位 + policyVersion。
- Event Consumer：eventId Inbox 唯一。

## 16. 可靠性与降级

### 16.1 故障域

| 故障 | 行为 |
|---|---|
| LLM 超时 | 返回确定性结果或可重试错误，不执行写动作 |
| Model Provider 不可用 | 只读解释可按策略 fallback；风险评分继续 |
| Sandbox 启动失败 | 更换 Sandbox 重试一次，随后降级为无代码分析 |
| Agent Session Redis 不可用 | 拒绝新 Run，不影响短链核心业务 |
| Python DB 不可用 | Agent 降级不可用，不影响 Gateway |
| Java Capability 不可用 | Tool 返回 unavailable，Agent 不编造数据 |
| Event Bus 延迟 | Action 最终一致，UI 显示处理中 |
| Risk Redis 写失败 | Outbox 重试，Gateway 使用最后有效策略 |
| Python 整体不可用 | Agent 页面降级，短链与已生效风控继续 |

### 16.2 重试原则

- 模型：只对明确可重试错误有限重试，受 Run deadline 限制。
- GET Capability：最多 2 次，指数退避和抖动。
- Proposal/Command：客户端不透明重试；依赖 idempotencyKey。
- Sandbox：仅基础设施失败允许重建一次。
- Outbox：指数退避、最大延迟、死信和人工 replay。

### 16.3 背压

必须设置：

- 每租户并发 Run。
- 每用户并发 Run。
- 全局模型并发。
- Sandbox 并发。
- Worker 队列深度。
- Tool 并发。

达到上限时返回可识别的 429/queued 状态，不得无限堆积内存任务。

## 18. 安全架构

### 18.1 威胁模型

必须覆盖：

- Prompt Injection
- Tool 参数注入
- SSRF
- 越权 gid 访问
- 租户会话串读
- Sandbox 逃逸
- Secret Exfiltration
- Delegation Token 重放
- 恶意文件
- 依赖供应链攻击
- 模型输出污染策略
- 日志和 Trace 泄密

### 18.2 数据分类

| 级别 | 示例 | 允许进入模型/Sandbox |
|---|---|---|
| PUBLIC | 公共域名、公开标题 | 可以 |
| INTERNAL | 聚合指标、非敏感配置 | 按策略 |
| CONFIDENTIAL | 用户业务统计、分组数据 | 脱敏和最小化后 |
| RESTRICTED | 原始 IP、Token、密码、连接串、个人身份信息 | 禁止 |

### 18.3 Prompt Injection 防线

1. 外部网页、URL title、Tool 输出均标记为数据。
2. System Prompt 声明不可接受数据中的指令。
3. Tool 选择受 allowlist、scope 和 schema 约束。
4. Java 再次授权并校验所有业务参数。
5. 模型不得看到 Command API。
6. 高风险输出必须结构化并通过确定性验证。

### 18.4 Secret 管理

- Secret 使用 Vault、KMS/Secrets Manager 或等价系统。
- 禁止进入环境转储、日志、Prompt、Checkpoint 和 Sandbox。
- 使用短期凭据和 workload identity。
- 密钥必须可轮换并支持双 key 过渡。

## 21. 测试与质量工程

### 21.1 测试金字塔

## 22. 成本治理

成本是运行时约束，不是上线后的统计项。

每租户配置：

- 每日模型 Token。
- 并发 Run。
- 最大 Agent 迭代。
- Sandbox CPU 分钟。
- Artifact 存储。
- 风险批次候选数量。

达到软阈值时告警，达到硬阈值时拒绝或降级。

优先使用确定性计算完成排名、聚合、比例和风险评分；模型只解释结果和处理自然语言。

| Sandbox/Runtime Security | Platform/Security |
| Java Capability/Approval | Admin Domain Team |
| RiskControl/Gateway Contract | Risk Domain + Gateway Team |
| Schema/Event Governance | Architecture Group |
| SLO/Runbook | Service Owner + SRE |

跨边界修改必须由双方 Owner 审核。

## 25. 关键架构决策

| ADR | 决策 |
|---|---|
| ADR-001 | Agent Runtime 使用 Python + AgentScope 2.0 |
| ADR-002 | Java 继续拥有业务事实和权威命令 |
| ADR-003 | 最终由 Browser 经 Gateway 直连 Python，使用 Delegation Token |
| ADR-004 | Sandbox 是独立执行面，不与 API 进程共置 |
| ADR-005 | Java/Python 不共享表所有权 |
| ADR-006 | 跨服务一致性使用 Outbox/Inbox，不使用分布式事务 |
| ADR-007 | 风险评分确定性，LLM 只负责解释 |
| ADR-008 | Gateway 热路径不依赖 Agent |
| ADR-009 | Authority 初期进入 admin 模块化单体，满足条件后再提取 |
| ADR-010 | AgentScope 被本地 Runtime Port 封装，不作为产品 API |

不可逆或高迁移成本决策：

- 数据所有权。
- 身份和租户模型。
- Gateway 风险策略契约。
- Approval/Policy 状态机。

可逆决策：

- 模型 Provider。
- Sandbox Backend。
- Event Bus 实现。
- Python Web Server 和具体 ORM Driver。

优先把精力投入不可逆决策。

## 27. 最终验收标准

最终架构完成必须满足：

1. Java agent-service 不再承载任何生产流量，模块可删除。
2. Python Runtime 通过 AgentScope 运行 Campaign Agent。
3. Risk Workflow 在无 LLM 时仍可完成确定性评分和持久化。
4. Browser 通过 Delegation Token 直连 Python，不存在同步服务调用环。
5. Python 无短链业务库和 Risk Policy Redis 写权限。
6. Sandbox 无业务网络和业务 Secret。
7. 所有 Command 均由 Java Approval/Authority 执行。
8. 同一 idempotencyKey 不产生重复动作。
9. 旧策略撤销不会删除 Redis 新版本。
10. Gateway 在 Python/LLM 故障时继续执行已生效策略。
11. 跨租户、跨用户、跨会话访问测试全部拒绝。
12. SSE 支持断线恢复和事件去重。
13. Outbox/Inbox 故障恢复通过。
14. 关键 SLO、告警、Dashboard 和 Runbook 就绪。
15. Agent 评估集、Sandbox 安全测试和迁移回滚演练通过。

## 28. 结论

优秀架构不是让所有能力都采用最新框架，而是让每种风险由最适合的边界承担。

本方案的最终形态是：

> AgentScope 和 Python 获得模型、会话、沙箱、多租户和 AI 生态的灵活性；Java 保留业务事实、事务、审批和网关策略的确定性；两者通过身份明确、版本化、可审计的契约协作。

该边界使系统同时具备：

- Agent 创新速度。
- 业务正确性。
- 生产故障隔离。
- 安全与租户隔离。
- 可演进的数据所有权。
- 可验证的工程质量。

任何后续设计都应证明自己没有破坏本文的不变量，而不是要求本文为局部实现让步。
